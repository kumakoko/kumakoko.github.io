EasyRoad3D-材质与着色器

简介

由于使用普通游戏对象并带有网格渲染器组件，您可以使用自己的材质和着色器，或 Unity 自带的着色器。

本包附带了一组着色器，利用了道路和侧边对象的各种 UV 控制。对于道路，可以在 uv4 通道上设置额外 UV 数据；对于形状类型侧边对象，可以设置顶点颜色以及在 uv4 通道上设置额外 UV 数据。

包中的着色器展示了如何在着色器中使用这些数据。

着色器

  • EasyRoads3D - Unity 5 Standard：这是 Unity Standard 着色器的副本，使用 offset（偏移）作为处理 z-fighting 的方式。偏移还防止当地形 LOD 系统生效时，道路在远离相机的地形中消失。
  • ER Dual Blend UV1：点击此按钮返回编辑模式。
  • ER Blend UV4：与下文非常相似，但使用 cutout（裁剪）而非 decal:blend（贴花混合）。
  • ER Dual Road Blend：I 连接器。
  • ER Road Decal Splat Blend：使用控制纹理和 UV4 细节数据将额外纹理与主纹理混合。
  • ER Road Detail：使用 UV4 细节数据将细节纹理与主纹理混合。
  • ER Road Transparency：完全透明，支持基于贴花混合的阴影。阴影的投影方式与在道路下方地形上投影类似。
  • Misc / ER Race Track：使用 uv4 数据将第二纹理与主纹理混合，同时混合平滑度纹理。可用于在赛道上定义完美的赛车线。
  • Misc / ER Road Splat 4 UV4：此着色器将轨迹纹理与模拟的地形纹理和地形 splatmap 混合。可用于具有更多几何细节的地形网格覆盖层。
  • Terrain / ER Terrain Mask：用于作为地形遮罩的对象。
  • Terrain / ER Custom Terrain：Unity 地形着色器的略微修改版本，支持使用遮罩对象挖洞。
  • Tesselation / ER Terrain Mesh Tesselation：此着色器将两个纹理与模拟的地形纹理和地形 splatmap 混合。在两个纹理上使用曲面细分。可用于地形网格覆盖层，如演示项目中的岩壁。

EasyRoad3D-道路对象层级

概述

在 v3 中，所有 EasyRoads3D 对象都是一个单一"道路网络（Road Network）“游戏对象的子对象，该对象可通过主菜单创建：

主菜单 > GameObject > 3D Object > EasyRoads3D > New Road Network（新建道路网络）

所有独立的道路对象将被添加到子游戏对象 Road Objects（道路对象）中。所有交叉口将被添加到游戏对象 Connection Objects（连接对象）中。分配给道路对象的侧边对象（Side Objects）将作为子对象添加到该道路对象下。

添加道路和交叉口时，应在层级窗口（Hierarchy）中选中主道路网络对象。

YooAsset HostPlayMode（联机热更模式）完整热更新流程

HostPlayMode是手游最常用模式，三套FileSystem协同工作

  1. BuildinFileSystem：安装包内StreamingAssets/yoo首包内置资源（只读兜底）
  2. CacheFileSystem：手机沙盒可读写目录，存放已经下载的AB包、清单
  3. RemoteFileSystem：访问CDN远程服务器下载补丁资源

前置：打包阶段输出补丁包，包含：version文件、PackageManifest(清单)、全部.bundle，全部上传CDN。

整体流程图（客户端启动后）

游戏启动 → YooAssets全局初始化 → Package初始化
→ ①请求远端PackageVersion版本号
→ ②更新本地Manifest资源清单
→ ③创建下载器，对比MD5/Crc，生成待下载列表
→ ④多线程断点下载AB包到沙盒缓存
→ ⑤切换激活新清单，完成更新
→ （可选）清理沙盒废弃缓存文件
→ 业务层LoadAssetAsync加载资源，进入游戏

分步详解（运行时每一步干什么）

步骤1：初始化YooAsset与Package

//全局初始化
YooAssets.Initialize();
var package = YooAssets.CreatePackage("DefaultPackage");

//HostPlayMode参数：内置文件系统、缓存文件系统、远程CDN文件系统
var hostParam = new HostPlayModeParameters();
hostParam.BuildinFileSystemParameters = FileSystemParameters.CreateDefaultBuildinFileSystemParameters();
hostParam.CacheFileSystemParameters = FileSystemParameters.CreateDefaultCacheFileSystemParameters(remoteService);
hostParam.RemoteFileSystemParameters = FileSystemParameters.CreateDefaultRemoteFileSystemParameters(remoteService);

await package.InitializeAsync(hostParam);
  • 初始化逻辑：优先读取沙盒缓存里的Manifest；沙盒没有就读取安装包StreamingAssets内置Manifest，拷贝到沙盒作为基础版本。此时还没有联网检查新版本，只是把本地旧版本加载就绪。

步骤2：RequestPackageVersionAsync 请求远端版本号

var verOp = package.RequestPackageVersionAsync();
await verOp.Task;
string remoteNewVersion = verOp.PackageVersion;
  • 向CDN请求version版本文件（很小的文本文件，记录当前线上Package的版本字符串）。
  • 拿到线上最新版本号；网络失败在这里弹窗提示重试。

⚠️version文件是整个热更的入口，每次打包补丁包都会生成新version。

步骤3：UpdatePackageManifestAsync 更新资源清单

var manifestOp = package.UpdatePackageManifestAsync(remoteNewVersion);
await manifestOp.Task;
  1. 拿远端版本号，去CDN下载对应的PackageManifest清单文件（几KB）。
  2. Manifest清单记录该Package下全部AB包、每个资源归属哪个AB、每个AB的MD5、大小、依赖关系。
  3. YooAsset对比：沙盒缓存已有哪些bundle、内置首包有哪些bundle。
    • 相同MD5：直接复用（不管来自沙盒缓存，还是来自APK内置StreamingAssets）
    • MD5不一致 / 本地不存在：标记为需要下载

✨增量更新的核心就在Manifest对比，不会全量下载，只下载变更/新增bundle。

YooAsset资源构建界面详解

**请尊重原作者的工作，转载时请务必注明转载自：kumakoko.github.io

YooAsset AssetBundleBuilder 构建界面选项详解（3.0.x官方文档）

打开路径：Window → YooAsset → AssetBundle Builder


1. Build Package（资源包裹）

  • 作用：下拉选择要构建的资源包裹(Package)，一个工程可以配置多个Package，相互完全独立。
  • 场景：项目多分包、多资源包隔离，只构建选中的包裹，不会影响其它包裹。 注意：打包前需要在AssetBundleCollector窗口配置好对应Package的收集规则。

2. Build Pipeline（构建管线）

决定打包执行逻辑，不同管线用途完全不同，管线种类如下表所示

管线详细说明使用场景
EditorSimulateBuildPipeline编辑器模拟构建，只生成资源清单，不生成真实AB包。模拟真实打包环境，跳过耗时的AB生成。开发调试，EditorSimulateMode模式，快速验证收集逻辑，不用真正打包。
LegacyBuildPipelineUnity传统内置打包管线，旧版本遗留。Unity2020及更早版本项目。
ScriptableBuildPipeline(SBP)Unity可编程构建管线，可自定义打包流程，打包速度、稳定性优于旧管线。Unity2021.3+强烈推荐生产环境使用
RawFileBuildPipeline原生文件管线，不经过UnityAB系统，直接复制原始文件。处理Unity不识别的文件：FMOD bank、自定义二进制文件等。
ArchiveFileBuildPipeline归档管线，把多个原始文件合并成单个归档文件。大量小原生文件，减少文件数量，方便管理加密。

3. Build Output（构建输出目录）

  • 作用：设置打包产物根目录。
  • 重要特性：工具会自动根据Unity编辑器当前选中的平台，在该目录下创建平台子目录（Android/iOS/StandaloneWindows等），不同平台产物互不干扰。
  • 产物目录结构示例：BuildOutput/Android/DefaultPackage/v1.0，里面存放AB包、清单、构建报告。

4. Build Version（构建版本）

  • 作用：本次资源包的版本号，补丁包文件夹名称就等于该版本。必须大于0，每次热更打包必须修改。
  • 运行时意义：客户端比对该版本号判断是否需要更新资源。

提示：版本号可以是数字字符串，例如1001、20260822。


5. Clear Build Cache（清理构建缓存）

  • 勾选：删除全部构建缓存，全量重新构建所有资源包，打包慢；修改打包规则、资源分组后建议勾选。
  • 不勾选：开启增量打包，对比上一次缓存，只重新打包发生变更的资源，打包速度大幅提升。

⚠️注意：修改收集规则、分组规则、管线参数时，增量缓存可能产生错误产物，需要勾选清理缓存。


6. Use Asset Depend DB（资源依赖数据库）

  • 开启：资源收集阶段读取缓存的依赖关系数据库，不用每次重新完整解析所有资源依赖，大幅提升收集阶段速度。
  • 关闭：每次打包完整扫描所有资源依赖，适合资源大量改动的调试阶段。

生产打包建议勾选，配合增量打包使用。


7. Bundle Encryptor（资源包加密器）

  • 作用：选择实现IBundleEncryptor接口的加密类，对输出的AssetBundle/Raw/Archive文件做加密处理。
  • 默认内置：YooAssetEditorEncryptionNone=不加密。
  • 自定义：自己写加密类，放到Editor目录，下拉框自动识别。

运行时必须配置对应的解密器，否则无法加载资源。

YooAsset Collector（资源收集器）完整详解

打开窗口：Window → YooAsset → AssetBundle Collector Collector（收集器）是YooAsset编辑器里最小配置单元，只存在编辑器阶段，运行时不存在。 它的职责：指定扫描哪个目录、筛选哪些资源、资源如何寻址、如何打成AssetBundle。 一个Group下可以有多个Collector；每个Collector代表一套独立扫描+过滤+打包规则。 层级回顾：Package → Group → Collector Package、Group、Collector都是编辑器配置；打包后全部转化为Manifest清单与物理AB文件。

Collector全部属性列表

属性说明
CollectPath收集路径，可以填文件夹路径，也可以填单个资源完整路径（Assets/xxx/xxx.prefab），必须以Assets开头
CollectorType收集器类型（3种，核心），决定资源是否写入Manifest清单，运行时能否直接LoadAsset加载
AddressRuleName寻址规则：生成运行时代码加载资源的key（逻辑地址），EnableAddressable开启后生效
PackRuleName打包规则：决定收集到的资源如何合并、拆分生成AssetBundle物理文件
FilterRuleName过滤规则：在CollectPath范围内再筛选文件类型，过滤掉不需要的资源
UserData自定义字符串，用于自定义PackRule/AddressRule/FilterRule，业务扩展用，内置规则不会读取此字段
AssetTags资源标签，分号分隔；用于打包时筛选拷贝到StreamingAssets首包、清单标签过滤等功能

1. CollectorType 收集器类型（最重要）

① MainAssetCollector【90%业务使用】

  • ✅资源写入Manifest资源清单

  • ✅运行时代码可以直接LoadAssetAsync<T>("逻辑地址")加载

  • ✅依赖分析正常生效，被引用的贴图材质会做共享包拆分

  • 适用：预制体、UI、场景、音频、Sprite图集，所有需要业务代码主动加载的资源。

    ② StaticAssetCollector

  • ❌不会写入Manifest，代码不能直接加载

  • ✅参与打包；无视共享依赖规则，不会被框架剥离为共享Bundle。

    无论多少主资源引用它，都会严格按照本Collector的PackRule打包，不会被拆分出去。

  • 适用场景：强制把一组贴图/材质固定打在同一个AB，不希望框架自动拆共享包。

    ③ DependAssetCollector

  • ❌不会写入Manifest，代码不能直接加载

  • ✅参与打包；没有任何主资源引用这些资源时，打包会自动剔除该资源，减小包体。

  • 适用场景：特效贴图、粒子纹理等只被别的资源间接依赖，业务不会直接加载的资源。可以做细粒度分包，修改一张纹理只更新小包。

    简单对比表

    类型写入清单可直接加载共享包机制特点
    MainAssetCollector✅✅正常生效业务主资源，绝大多数场景
    StaticAssetCollector❌❌关闭强制打包，不做共享剥离
    DependAssetCollector❌❌正常生效无引用自动剔除，用于依赖资源

YooAsset Package（逻辑资源包）与Group(分组)详解

请尊重原作者的工作，转载时请务必注明转载自：kumakoko.github.io

YooAsset Package（逻辑资源包）与物理AB文件关系

Package是纯逻辑概念，它和AssetBundle文件没有固定一一对应关系。一个 Package（逻辑包）可以对应N个物理AssetBundle文件，数量完全由打包规则PackRule + 共享依赖拆分规则共同决定。

层级梳理：

Package(逻辑包，运行时代码拿到的对象)
├─ Group（分组）
│  ├─ Collector收集器（配置路径、PackRule分包规则）
│  │    → 根据PackRule生成若干个AssetBundle物理文件
└─【自动生成】共享依赖Bundle、Shader专用Bundle（不在Collector里配置）


1. PackRule 直接决定Collector产出多少AB文件


PackRule行为产出AB数量
PackSeparately每个资源文件单独1个AB收集多少主资源，就生成多少AB
PackDirectory每个子文件夹1个AB收集路径下子文件夹数量
PackTopDirectory收集路径下第一层文件夹各自一个AB一级子目录数量
PackCollector当前Collector全部资源合并为1个AB固定1个
PackGroup当前Group下所有Collector全部合并成1个AB固定1个

注意：以上只是主资源生成的AB数量，还会额外产生共享依赖Bundle，这部分是YooAsset自动生成，你在Collector界面看不到配置。



2. 额外自动生成的AB包（很关键，容易被忽略）

开启 EnableSharePackRule（默认开启，零冗余模式）时：

  • 如果一个贴图/材质被≥2个不同AB包引用，这个依赖资源会被剥离出来，生成独立的共享AssetBundle，避免多份拷贝冗余。
  • 开启自动收集Shader：所有shader会统一打入一个专门的Shader‑Bundle文件。

👉 所以：哪怕你把Group设置为PackGroup（全部主资源打为1个AB），最终Package下面也可能不止1个AB，还附带若干共享依赖Bundle、Shader Bundle。

举个直观例子

  • 1个Package，1个Group，PackGroup规则：所有主资源合并成1个主AB。
  • 但是里面10张贴图被多处预制体共用。
  • 打包结果：
    • 1个主资源AB（所有prefab场景）
    • N个自动生成的共享依赖AB（被多个地方引用的贴图材质）
    • 1个Shader Bundle

最终这个逻辑Package，实际对应物理磁盘上：1+N+1个.bundle文件。


3. 运行时视角

代码中你操作的是：


var package = YooAsset.GetPackage("DefaultPackage"); //逻辑包对象

package内部持有一份Manifest清单文件。清单记录了这个逻辑包管辖的全部AssetBundle列表、每个资源属于哪个AB、AB之间依赖关系、MD5、大小等信息。Manifest是逻辑包和物理AB文件的桥梁；多个物理AB全部归属同一个Package管理，统一更新、统一缓存。


4. 容易混淆概念总结

  1. Package：逻辑业务单元，可以独立更新，一个Package对应一份manifest清单，不限制底层AB数量。
  2. Group：编辑器配置分组，仅编辑器用，运行时不存在Group对象。
  3. Collector：定义哪些资源被收集，以及分包策略PackRule。
  4. AssetBundle：磁盘真实物理文件，一个Package下面可以几十/几百个AB文件。

❌错误理解：一个Package等于一个AssetBundle文件 ✅正确理解：一个Package = 一份Manifest + 一批属于此Package的物理AB文件集合。AB数量取决于你的PackRule，以及共享依赖拆分。

EasyRoad3D-通用工作流

简介

EasyRoads3D v3 系统旨在最大限度地减少您在场景中为每条道路或交叉口在 Inspector（检查器）中设置参数和属性所需的时间，从而最大化工作效率。

在开始创建道路之前，建议先设置道路类型和材质。您随时都可以扩展可用的道路类型、材质和交叉口预制体，但从这里开始是个好习惯，这样您就可以设置好主要的道路类型，并在场景中快速调用。

推荐的工作流程取决于您项目的性质，以及您是想使用自己的道路类型、材质、交叉口类型，还是想使用 EasyRoads3D 自带的默认选项。

如果您想使用自己的材质和交叉口，建议阅读本节。

此外，EasyRoads3D 使用普通的 游戏对象（gameobjects） 以及 Unity 地形对象（Terrain Object）。建议您对这些对象及其组件（网格过滤器 MeshFilters、渲染器 renderers、碰撞体 colliders 和 材质 materials，以及地形基于网格的特性、高度图缩放 heightmapscale——它会影响地形网络更新地形的方式）有基本的了解，以便快速熟悉本工具。

步骤 1. 道路材质

在场景中创建新道路，或在常规设置中创建新道路类型时，您可能想为这条新道路分配特定的材质，如沥青、泥土/碎石等。在 Unity 中，这通过在项目面板和 Inspector 中通过拖放操作创建新材质，并为新材质分配纹理和着色器来实现。

在 EasyRoads3D v3 中，可以通过先准备好您的材质，并分别将它们存储在以下目录中来改进此工作流程：

  • /Assets/EasyRoads3D/Resources/Materials/roads
  • /Assets/EasyRoads3D/Resources/Materials/crossings
  • /Assets/EasyRoads3D/Resources/Materials/roundabouts

这是可选的。

每当创建新的道路类型时，您可以从 Inspector 中可用的材质下拉菜单中快速选择材质，或者例如在自定义交叉口编辑器窗口中选择。

步骤 2. 道路类型

可以通过"添加新道路"选项卡 在场景中创建新道路。可以设置道路宽度和材质。

但是，建议在 常规设置 > 道路类型 中设置道路类型。这些道路类型将可以在"添加新道路"选项卡的"道路类型"下拉菜单中选择。这在创建包含需要重复使用的不同类型道路的道路网络时特别有用。

World Streamer 2的Streamer类的作用分析

Streamer 类的作用分析

Streamer 是 WorldStreamer 2 插件的核心流送控制器，负责在大型开放世界中根据玩家位置异步加载/卸载场景瓦片（Scene Tiles），是整个场景流送系统的"大脑"。

一、核心定位

Streamer 继承自 MonoBehaviour（或 AtavismStreamer，当定义 AT_STREAMER2 时用于 Atavism MMO 框架），挂在场景中的 _Streamer_Major / _Streamer_Minor 物体上。它不直接存储瓦片数据，而是作为调度者，协调多个子系统完成流送。

二、主要职责

1. 玩家位置追踪 & 网格判定

  • 通过协程 PositionChecker() 每隔 positionCheckTime（默认 0.1 秒）轮询玩家位置
  • CheckPositionTiles() 调用各 SceneCollectionManager.CheckPosition 判断玩家是否跨入新的网格单元
  • 若发生变化，则触发加载与卸载

2. 场景瓦片加载

  • SceneLoading() 以螺旋遍历方式扫描玩家周围 loadingRange 范围内的瓦片，将未加载的瓦片加入 scenesToLoad 队列
  • 支持环形流送（useLoadingRangeMin 挖空中心区域）
  • 支持世界循环（looping，通过 mod 取模实现坐标回绕）
  • LoadLevelAsyncManage() 在 Update 中按优先级排序队列，受 maxParallelSceneLoading 限制并发数，并通过 sceneLoadWaitFrames 做帧间隔控制

3. 场景瓦片卸载

  • SceneUnloading() 延迟 destroyTileDelay 秒后执行，遍历已加载瓦片，超出 deloadingRange 的加入销毁列表
  • 支持跨层联动卸载（unloadRangeConnect，当某层瓦片加载时卸载另一层对应位置瓦片）
  • 卸载后调用 TerrainNeighbours.CreateNeighbours() 修复地形 LOD 边界

4. 资源卸载

  • UnloadAssets() 以协程节流方式调用 Resources.UnloadUnusedAssets()，间隔 waitTillNextUnload（20 秒），避免频繁调用造成卡顿

5. 世界原点重置（Floating Origin）

  • 集成 WorldMover，玩家移动一定距离后将整个世界反向平移，避免浮点数精度问题
  • currentMove 记录累积偏移量，加载瓦片时据此修正位置

6. 加载进度 & UI

  • tilesToLoad / tilesLoaded / LoadingProgress 提供加载进度
  • 可选显示 UILoadingStreamer 加载界面

三、协作关系

协作类职责
SceneCollectionManagerScriptableObject，存储瓦片配置（尺寸、范围、场景名列表），维护 scenesArray 字典和 loadedScenes 列表
SceneSplit单个瓦片的数据结构（位置、场景名、加载状态、循环偏移）
StreamerLoadingManager实际执行 SceneManager.LoadSceneAsync/UnloadSceneAsync，管理加载/卸载状态机，避免同时操作
WorldMover世界原点重置
TerrainNeighbours地形相邻关系修复

四、典型工作流

Start()
  └─ PrepareScenesArray()  // 构建瓦片字典
  └─ PositionChecker() 协程
       └─ 每 0.1s: CheckPositionTiles()
            ├─ 玩家跨格? 
            │    ├─ SceneLoading()  → 螺旋扫描 → scenesToLoad 队列
            │    ├─ SceneUnloading() (延迟) → 超范围瓦片 → 卸载队列
            │    └─ WorldMover.CheckMoverDistance()
Update()
  ├─ LoadLevelAsyncManage()  // 消费 scenesToLoad，按优先级+并发限制提交加载
  └─ loadingManager.Update()  // 执行实际异步加载/卸载

五、总结

Streamer 是整个场景流送系统的调度中枢：它以玩家位置为驱动，以网格为单位，通过螺旋加载 + 范围卸载的策略，实现了一个可配置、支持多层/循环/环形流送的大型世界场景管理系统。实际的异步 IO 操作委托给 StreamerLoadingManager，瓦片元数据存储在 SceneCollectionManager 中，Streamer 本身专注于**“何时加载/卸载哪些瓦片"的决策逻辑**。

World Streamer 2 最本质的方法理念

问：从代码来看，WorldStreamer插件，其本质是不是把大场景分割成小块，然后用一套组织方式和加载方式，动态地只加载玩家视野范围内的若干小块？

从代码来看，WorldStreamer插件的核心原理确实是：把大场景分割成小块，然后动态地只加载玩家视野范围内的若干小块。详细解释如下：

  1. 场景分割阶段：

    • 编辑器中有一个 SceneSplitter 工具，将大场景按网格分割成多个小块场景
    • 每个小块场景以命名规则存储，如 Scene_x0_y0_z0、Scene_x1_y0_z0 等
    • 每个小块有固定的尺寸（xSize, ySize, zSize），比如默认500x500x500

  2. 组织方式：

    • 使用 SceneCollectionManager（ScriptableObject）来管理一个场景集合
    • 场景集合中存储了所有分割后场景的名字数组 names[]
    • 通过 PrepareScenesArray 将场景名字转换为 Dictionary<Vector3Int, SceneSplit>，键是网格坐标，值是SceneSplit对象
    • 支持多层场景集合（如地形层、植被层、建筑层等），每层独立控制加载范围

  3. 加载方式：

    • Streamer 组件挂载到场景中，引用玩家对象
    • PositionChecker 协程定期（positionCheckTime，默认0.1秒）检查玩家位置
    • CheckPosition 计算玩家当前所在的网格坐标（通过 pos / size）
    • 当玩家跨越网格边界时，触发 SceneLoading 和 SceneUnloading
    • SceneLoading：以玩家所在网格为中心，按螺旋顺序遍历 loadingRange 范围内的所有网格，将需要加载的场景加入 scenesToLoad 列表
    • LoadLevelAsyncManage：每帧管理加载队列，控制并发加载数量
    • StreamerLoadingManager：实际执行异步场景加载（SceneManager.LoadSceneAsync Additive模式）和卸载
    • 加载完成后，将场景根对象移到正确的世界位置

  4. 卸载方式：

    • SceneUnloading：检查所有已加载场景，如果超出 deloadingRange 范围，则加入卸载队列
    • StreamerLoadingManager.UnloadAsync：异步卸载场景
    • 还会调用 Resources.UnloadUnusedAssets() 清理内存

  5. 其他特性：

    • 支持循环世界（looping）：当玩家到达边界时，从另一边绕回来
    • 支持环形加载（useLoadingRangeMin）：可以设置内部不加载的范围
    • 支持多层场景集合的联动卸载（unloadRangeConnect）
    • 支持碰撞体流（ColliderStreamer）：可以单独流加载碰撞体场景
    • 支持地形邻居连接（TerrainNeighbours）
    • 支持WorldMover：将整个世界向玩家移动，避免浮点数精度问题

所以提问者的理解基本正确，但需要补充一些细节：

  • 不仅仅是"视野范围"，而是一个可配置的加载范围（loadingRange）和卸载范围（deloadingRange）
  • 加载范围通常比视野大，是提前加载的缓冲区
  • 支持多层独立流加载
  • 支持循环世界
  • 有异步加载队列管理，控制帧率
