引言（Introduction to World Streamer）

World Streamer 是一个内存异步流式加载系统（memory ASYNC streaming system）。通过使用它，可以在任意轴和空间中从磁盘流式加载的整个游戏。可以创建无尽太空游戏、2D 平台跳跃游戏、第三人称游戏、开放世界、移动端应用、建筑漫游展示、单机、多人游戏，或任何想要的游戏类型——玩家移动过程中不会有加载画面。还可以创建无尽循环的世界或星球模拟。甚至可以为的游戏生成远距离背景。

所有场景资产将作为场景文件存储在磁盘上，只有当足够接近它们或它们满足所需条件时才会被加载。这个方案降低了 CPU、RAM、VRAM 和 GPU 的使用率，游戏的性能会好得多，加载应用程序也会快得多。通过流式加载，会减少场景中的对象数量，可以创建非常精细的大型场景而不会掉帧。World Streamer 让能够不受任何限制地创建想要大小的场景。

Floating Point Fix System（浮点修复系统） 消除了引擎中因超大坐标引起的限制和错误。借助 Local Area Updater（局部区域更新器），可以在不加载整个世界的情况下，在一个小的局部区域工作，只需点击几个按钮就能轻松把这些修改加入世界。这意味着不会因为把整个世界加载进编辑器场景而导致 Unity 编辑器变慢。

还可以把世界分成多个层，如 Lighting（光照）、AI、Geometry far in the distance（远景几何体）、Geometry Near（近景几何体）、Trees（树）等。Ring Streaming（环形流式） 让能够把远处的对象替换为更低 Level Of Detail（LOD）的模型。可以把精细的地形替换为远处的低多边形网格植被。

Collider Streaming（碰撞体流式加载） 让能够在足够接近建筑、房间、洞穴、室内等物体时才加载它们——当进入/撞击到触发它们的碰撞体或传送门时。

World Streamer 是团队在同一项目上同时工作的完美解决方案，即使在同一个区域也可以。团队成员可以分别在世界的不同区域工作，然后使用 Local Area Updater 在完成后把各自的修改保存进世界。团队成员也可以在同一区域同时工作——通过在不同的层上工作。

应社区要求，提供了这份详尽的手册来全面解释一切；但一旦理解了基础，将只需要点击几个按钮、花几分钟甚至几秒钟，就能为流式加载准备好的游戏。

如果想使用 HD 或 URP，请打开 “HD and URP Support Packs” 文件夹，按照 readme 文件操作，从该文件夹中导入适合 HD 和 URP 版本的支持包。

1. 流式加载的理念——非常重要

这个理念相当简单：巨大世界会被工具切分成较小的部分。这些部分就是虚拟网格上的元素。当某个"对象"（玩家或其他对象）足够靠近网格元素时，World Streamer 会加载这些虚拟网格元素。还可以在玩家撞到碰撞体时加载网格元素（碰撞体流式加载）。

大多数情况下，建议使用玩家作为这个"对象"，而不是相机。对于 RTS 游戏或 2D 平台游戏，把相机设为跟随对象是更好的方案。

因为是把一切都保存为场景，仍然可以使用 lightmap、navmesh、GI、合批、烘焙碰撞体，以及一切可以保存在场景中的东西。可以使用自定义剔除方案，或通过在对象足够远或位于墙后时把它们从内存和场景中移除来剔除对象。作为流式剔除对象的例子：可以只在靠近时加载小石头，或者用碰撞体流式加载只在到达正确楼层或靠近入口时加载建筑内部。

借助 World Streamer，可以根据距离用另一个层的网格元素替换某个网格元素。可以把它用作 Unity LOD 系统不支持的对象、或 LOD0 很重的对象（如 Unity Terrain）的 LOD 方案。可以在远处的 Unity Terrain 替换成简单网格——这种网格甚至可以包含树——这将大幅减少剔除和刷新操作（CPU）以及内存使用。Unity Terrain 可能非常重，所以这可以节省数百 MB 的 RAM。更多关于处理 Unity 地形、对象等信息见手册后文。

World Streamer 可以分层流式加载，这意味着可以把不同对象放在不同层上。例如，可以有一个地形层、一个树层、一个岩石层、一个音效层。每层独立加载对象。

用好层的一个好办法是按尺寸对对象分组：只把小型对象加载在玩家附近，而把较大的对象加载在远处。例如，需要在远处看到的建筑可以放在它们自己的层；中等尺寸的细节（如箱子和灯笼）可以加入 “Medium”（中距离）层；而更小的细节（如纸张、泥土、小石头）放在它们自己的层。对于地形，玩家附近使用精细地形层，玩家远离地形时，显示一个包含地形低模网格的独立层。

如果把所有这些东西放在不同层上，就可以设置每个对象（层）在 RAM、VRAM、CPU、GPU 中可见和驻留的距离。这是一个动态设置，可以在游戏过程中为玩家管理它。每层及其流式范围都可以独立配置，甚至每个轴方向 X、Y、Z 都可以有不同的流式范围设置。层还可以用来把灯光、粒子和其他特效与 3D 内容分开。这允许多个团队成员同时在同一张地图和区域上工作。

把世界切分成多个部分后，始终可以用 Local Area Updater 工具重新创建一个大而未切分的场景。这意味着随时可以撤销世界的碎片化，把任何修改合并回一个完整的场景。

基本理念就是：把世界切分成许多不同层的虚拟网格元素，然后异步加载它们，对 CPU 零冲击，从而在 CPU、GPU、RAM 和 VRAM 上节省大量性能。

记住：World Streamer 的真正威力在 build（构建）中体现。 在构建过程中，Unity 编辑器烘焙许多东西，如碰撞和合批。如果在编辑器中使用 World Streamer，这些操作必须在运行时进行，有时它们不是异步的，或者干脆说它们很重。可以通过临时关闭静态合批等来减少这些尖峰——但只在编辑器中。会在编辑器里损失性能（drawcall 会增加）。然而在构建中，一切都会很好。

2. World Streamer 项目要求

  • 必须向项目添加以下标签（Tags）：
    • SceneStreamer —— 必须分配给任何使用 Streamer.cs 脚本的 GameObject。_Streamer_Major 和 _Streamer_Minor 预制体必须具有 SceneStreamer 标签。
    • WorldMover —— 必须分配给任何使用 WorldMover.cs 脚本的 GameObject。_World_Mover 预制体必须具有 WorldMover 标签。
    • ColliderStreamerManager —— 必须分配给任何使用 ColliderStreamerManager.cs 脚本的 GameObject。_Collider_Streamer_Manager 预制体必须具有 ColliderStreamerManager 标签。

⚠️ 这些流式系统预制体必须全部有标签！ 如果不添加它们，World Streamer 在构建中甚至编辑器中都无法加载任何内容。如果没有添加所需标签，会得到很多错误。在新项目中始终检查标签！

  • Incremental GC（增量 GC） 在项目设置——Player Settings 中使用 Incremental GC（增量 GC） 选项——这会大大加快流式加载速度——记住要保持开启。
  • Prebake Collision Meshes（预烘焙碰撞网格）：此选项在构建时加快流式加载，但会拖慢编辑器，因为 Unity 会把网格烘焙成块。它能大幅降低物理开销。

  • 要开始，需要一个 “Work” 场景，其中保存所有将从磁盘流式加载的模型。这个场景（或多个场景）将用于把世界切分成虚拟网格元素、多个层。
  • 关于 Streamer 如何识别模型/对象和地形的所有信息，请查看手册相应章节。
  • 要进行流式加载，需要一个 “Gameplay” 场景，其中保存：玩家、方向光、相机、 UI；其他一切（世界）都可以从磁盘加载。会把 Streamer 预制体放在那里，它会加载想要的一切。请在开始前准备好它。当世界被切分成多个部分后，会填充 Streamer 预制体。

3. 快速上手——测试场景（Quick Start - Test Scene）

1. 必须配置正确的标签才能使用演示场景——请查看 《2.World Streamer 项目要求》一节。所有提到的 Streamer 系统预制体都必须有标签！ 如果不添加它们，World Streamer 在构建中甚至编辑器中都无法加载任何内容。缺少标签会得到很多错误。在新项目中始终检查这一点！

2. 打开任意 Gameplay World Streamer 演示场景：“WorldStreamer” 目录 → “Tutorial Work and Game Scenes” → 选择 Game 场景。

准备了移动端和独立平台的场景，以几种变体展示、开启了不同功能，请选择适合场景。

3. 将当前场景加入 Build Settings：点击层级中的 streamer 对象，点击 “Add to Build Settings”（加入构建设置） 按钮。必须把所有网格元素（场景）放进 Build Settings。没有这一步，无法加载它们。

4. 由于场景也通过碰撞体流式加载模型，必须把带建筑内部的场景加入 Build Settings：“WorldStreamer” 目录 → “SplitScenes” → “ColliderScenes” → “Prefabs” → 点击 “Collider Stream Interior_stream” 预制体及其他预制体，然后点击 “Add to Build Settings” 按钮。对其他预制体做同样的操作。 5. 点击 Play 或构建项目，四处跑一跑，看看一切都是如何流式加载的。建议做一个构建（build），因为播放模式会被通常在构建期间进行的操作（如合批、碰撞烘焙等）拖累。

当然，有更简单、更自动化、更快的方法来做这件事，但现在想展示一些系统工作原理的基础信息。

4. World Streamer 细节与设置

流式解决方案由以下部分组成：

  • Scene Manager（场景管理器）：这个大型工具用于从场景对象创建虚拟网格和层，也用于管理光照设置、切分地形、按块管理地形。Scene Manager 还会从虚拟网格元素生成场景。在场景生成过程中，场景切分器（Scene Splitter）还会创建场景集合（Scene Collection）——为每一层创建一个。
  • Scene Collections（场景集合）：这些预制体保存关于场景、网格元素尺寸、世界尺寸等信息，以及许多对流式过程有用的细节。如前所述，它们由场景切分器或 Local Area Updater 工具在场景生成过程中创建并刷新。
  • Scene Objects（场景对象）：它们与场景集合相关联，由场景切分器或 Local Area Updater 工具在场景生成过程中创建并刷新。
  • Streamer 预制体：它们持有并使用场景集合，位于的 “Gameplay” 场景中，按照设置的选项流式加载内容。它持有想要流式加载的层。可以把所有内容放在一个 Streamer 中，也可以使用多个 Streamer 对象。
  • Collider Streamers（碰撞体流式加载器）：持有场景，在所选对象撞上它的碰撞体后加载该场景。
  • Collider_Stream_Manager（碰撞体流式管理器）：一个预制体，让能够通过 Collider Streamer 流式加载对象。这个对象还允许从隐藏在网格元素中的碰撞体流式加载场景。是的，可以创建套娃式流式结构（被流式加载的场景再去流式加载场景）。
  • Local Area Updater（局部区域更新器）：这个工具让能够合并场景、只加载局部区域、刷新/修改/移除已切分世界的部分。它让开发者们能够在同一区域、同一时间协同工作。
  • Streamer GUI：加载画面、传送、重生、位置调试 UI，可以修改并适配到的游戏结构。
  • World_Mover：这个对象用于浮点修复系统，负责重置世界位置；它还保存真实世界位置与重置后的本地世界位置之间的连接（差值）。这个连接对生成的（spawn）对象或服务器通信很有用。
  • Player_Mover：这个脚本用于在初始数据加载/传送结束前，把玩家移动到安全位置。
  • Player Teleport（玩家传送点）：持有重生/传送点位置的对象。这可以是一个动态对象。
  • Object to Move（待移动对象）：这个脚本保存非流式对象与玩家之间的关系，供浮点修复系统重置位置时使用。
  • TerrainCullingSystem（地形剔除系统）：这个脚本为地形渲染和流式加载提供额外性能提升。
  • Physic Culling System（物理剔除系统）：这个脚本保持/冻结动态物理对象，直到玩家足够接近。它会保存对象的方向和速度向量。这有助于避免因该区域数据尚未加载而导致的碰撞丢失情况。
  • Object Parent（对象父级）：如果想在切分过程中使用目录（catalog）结构，这个脚本应附加到层级目录（父对象）上。它让即使在切分过程中也能把对象保存在父级下。

4.1 Scene Manager（场景管理器）

这个工具用于把世界对象切分成虚拟网格，并准备进行流式加载。这里的"对象"指：模型、对象、灯光、粒子、地形。每个网格元素（“grid eye”）将是一"包"数据，World Streamer 把它作为一个整体对象加载进内存。

建议在一个空场景中打开 “Scene Manager”，将这个场景称为 “Work” 场景。应该把想要流式加载的全部内容复制进去。方向光、玩家、UI 应放在的 “Gameplay” 场景，所以把它们从 Work 场景移除，或在切分过程中隐藏。如果正确设置了层，这些对象也可以留在原处。

要打开 “Scene Splitter”（场景切分器）窗口，点击 Tools → Nature Manufacture → World Streamer → Scene Manager。

打开 “Scene Manager” 窗口后，会看到几个分区：

  • Terrain Manager（地形管理器）——准备地形进行流式加载：切割、生成低模网格等
  • Streaming Layers（流式层）——准备流式块并生成场景
  • Light Manager（光照管理器）——为流式场景设置光照选项
  • Build Settings（构建设置）——把场景、碰撞体流式加载器加入 Build Settings

4.1.1 Terrain Manager（地形管理器）

Terrain Manager 将准备的地形进行流式加载，例如切割地形。它也有助于估算地形块数量、全局修改地形草/树设置、为远距离的地形和树烘焙低模网格。

Terrain Settings（地形设置）：这是地形切分后每个地形块将获得的基础地形设置。如果已有分块的地形，可以同时更改所有地形的设置。

Terrain Splitter（地形切分器）：无需任何外部工具即可把地形切分成块。选择每个地形切分多少次。例如：1000×1000 的地形、513 高度图，切分 2 次会得到 4 个尺寸 500×500、257 高度图分辨率的地形。

Add Terrain Culling（添加地形剔除）：为所有地形添加剔除脚本，它会在相机看不到地形时关闭它们，提供额外的性能提升。

Terrain Low Poly Mesh Generator（地形低模网格生成器）——这个非常重要的工具能够从的地形（包括树）创建低模网格。记住：从树生成的低模网格只适用于 NM 树，因为它们带有正确的 shader。它们也可能适用于最后一 LOD 为 cross 面片模型的树。基本上，对于树，取最后一 LOD，用正确的 shader 烘焙成一张单一网格。移动端示例 Demo 中包含来自非 NatureManufacture 技术树的 cross 模型。

Terrain Low Poly Mesh Generator的设置（Settings）：

  • Ambient Color（环境色）——自动设置以达到最佳效果，但可以通过它控制生成的低模地形颜色。
  • Terrain Mesh Name（地形网格名称）——低模网格未来的名称。
  • Terrain LOD——低模网格的密集程度，默认设为 3，大多数情况下足够了。
  • Use Basemap（使用基础图）——决定生成的地形纹理来自 basemap 还是 splatmap。对于 CTS 等自定义 shader，建议使用 splatmap。如果在比地形瓦片尺寸更短的距离内渲染 basemap，请勾选此选项。
  • Use Smoothness（使用光滑度）——决定地形光滑度贴图是否保存到 basemap 的 alpha 通道。
  • Basemap Resolution（基础图分辨率）——为从地形生成的低模网格选择纹理分辨率。
  • Normal Details（法线细节）——系统还为低模网格烘焙法线贴图，以提供最准确的地形表现。用这个值决定地形的法线贴图应有多精细。默认设为最佳值，效果应该是最好的。
  • Normal Strength（法线强度）——决定低模地形的法线贴图应有多锐利。
  • Create normal from shape（从形状创建法线）——可以从地形形状创建法线贴图，这样会更准确。
  • Create normal from texture（从纹理创建法线）——从地形纹理创建法线，如果勾选，会与形状法线混合。
  • Y Offset（Y 偏移）——这个值让低模网格相对于原始地形略微下移。
  • Vertex down distance（顶点下移距离）——为避免低模网格与原始地形之间出现缝隙，把地形边界处的顶点下移。这个值决定地形周围这堵"墙"的长度。
  • Tree Prototypes（树原型）——系统读取地形中的树原型，可以把它们转换为低模网格，这样树在远距离不会消失，而且只占少量批次。记住：不是所有树都应该转换为低模网格。例如，很早就会消失的小树转换了反而是浪费资源。在示例中，可以关闭那些不应被烘焙的小树（small tree plant）。系统会取预制体的最后一 LOD，烘焙成一张大的单一网格。结合 cross 方案，效果非常完美。
  • Export 按钮（导出）——把地形导出为低模网格：带树、不带树、或仅树。可以决定怎么做。

4.1.2 Streaming Layers（流式层）

这部分会把所有对象切分成虚拟网格，并从中创建流式场景。

  • Add Layer（添加层）按钮：创建一个对象组/层。层把指定对象与其他对象分开，该层/组将独立于其他层流式加载。作为层/组的例子，可以使用：Terrains（地形）、Small models（小模型）、Big models（大模型）、Medium models（中模型）、Far low poly Terrains（远景低模地形）、Lights（灯光）、Particles（粒子）、FX（特效）。

  • Split X、Split Y、Split Z 按钮：让选择在虚拟网格生成时使用哪些轴。如果做太空游戏，很可能勾选 X、Y、Z；如果做 RTS、RPG、赛车游戏，很可能只勾 X 和 Z，因为高度没那么重要。对于 Unity Terrain，应该只勾 X 和 Z。如果想让玩家飞得过高时卸载地形，可以再勾 Y。

  • X size、Y size、Z size 数值：决定单个虚拟网格元素（“eye”）的尺寸。创建的虚拟网格基于勾选的 Split X/Y/Z 轴及其尺寸。网格元素尺寸应由估算。可以轻松更改并测试不同数值。它们不应太大——因为会一次加载太多对象；也不应太小——因为会有海量场景，而这些场景多半是不必要的。还必须把它与对象尺寸对照：如果的大建筑是 200×200 单位，就不应该用 20×20 的网格元素尺寸来流式加载它，但可以把一组这样的建筑放在 1000×1000 的虚拟网格元素中流式加载——当然前提是它们作为单个网格元素不算太重。

对于 Unity Terrain，“X size” 和 “Z size” 应该/必须与地形长宽相同。更多关于 Unity Terrain 的信息见 《5. Terrain streaming》的 《5.2 场景切分与虚拟网格设置》一节。

可以用 Gizmo 可视化虚拟网格元素尺寸。点击 “Split Scene” 或 “S” 按钮后，当点击系统刚创建的虚拟网格元素时，会看到它的边界。在此之前，必须填好虚拟网格和层的所有信息，才能创建第一次切分。

  • GameObject Prefix（游戏对象前缀）：这是非常重要的值。切分时系统会搜索对象，因为它想把它们放入正确的层，它会检查每个对象的名称。如果把游戏对象前缀留空，系统会把场景中的所有对象放入一个层。如果想按层级中的指定文件夹切分对象，需要把 “Object Parent” 脚本添加到文件夹中，并在脚本中设置与场景层相同的前缀。(这里的意思是指，点击Streaming layers界面创建层时，工具会检查场景中的对象的名字，如果它的名字是由GameObject Prefix选项指定的字符串开头的话，就表示该对象会选入到此层)

    • X——单独删除这一层

  • Gizmo color（Gizmo 颜色）：当点击虚拟网格时，场景切分器会用指定的颜色显示它们的边界。这个 Gizmo 颜色在 “Gameplay” 场景中还有助于可视化每一层的流式范围。

  • Generate Scenes from Colliders only（仅从碰撞体生成场景）：点击此按钮时，如果已准备好用于碰撞体流式加载的对象，系统会为碰撞体流式系统生成 “Collider_Stream” 预制体和场景。更多信息见 “7. Streaming by Colliders（通过碰撞体流式加载）“一节。

4.1.3 Lighting Settings 选项（光照设置）

这是为生成的场景设置的。可以为它们设置特定的光照选项，这样所有场景都会包含相同的 lightmap、烘焙 ambient 等设置。这可以避免流式加载过程中的警告和错误。它还可用于**切分的 Light Probe（光照探针）**并把它们分发到流式场景中。

Scene Collection Manager（场景集合管理器）——在这里拖放应与光照探针关联的场景集合。光照探针会被切成与所选层相同尺寸的部分，并被移动、重命名为正确的层切分目录。看上图。该层包含光照探针和地形。此过程之后必须重新生成该层。源光照探针网格会在场景中被禁用/关闭，只保留分块后的探针，以避免重复、混乱的探针。

其余设置用于为场景设置特定的光照选项，如雾等。基本上，初始设置取自当前 Work 场景，所以如果 Work 场景的设置正确，就不需要用到它。

4.1.4 Build Settings 选项（构建设置）

  • Scene Collections（场景集合）：在这里可以拖放场景集合预制体，把它们的全部内容批量加入 Build Settings。如果在 “Work” 场景中打开此窗口，它会自动填入在该 Work 场景中创建的所有场景集合。

  • Collider Streamers（碰撞体流式加载器）：在这里可以拖放 “Collider_Stream” 预制体，把它们的全部内容批量加入 Build Settings。如果在 “Work” 场景中打开此窗口，它会自动填入在该 Work 场景中创建的所有 “Collider_Stream” 预制体。

  • Add scenes to build settings（将场景加入构建设置）：点击此按钮，会把 “Scene Collections” 和 “Collider Streamers” 列表中的所有场景加入 Build Settings。

  • Remove scenes from build settings（从构建设置移除场景）：点击此按钮，会把 “Scene Collections” 和 “Collider Streamers” 列表中的所有场景从 Build Settings 中移除。

4.2 Streamer 对象/预制体及其设置

  • Active（激活）：可以激活或停用该层参与流式加载。
  • Priority（优先级）：设置各层流式加载的顺序，系统从最低值开始到最高值。
  • Scene Collection（场景集合）：这里把流式系统与的场景集合预制体连接起来——场景集合预制体保存关于虚拟网格元素（场景）的信息。直接把场景集合预制体拖进这个窗口即可。场景集合预制体位于它所属的、已生成场景所在的目录中，即 WorldStreamer → SplitScenes → 层名。
  • Loading Range（加载范围）：一个按每个轴设置的整数值，指定希望同时保存在 RAM 内存中的虚拟网格元素半径。加载范围可以在世界的每个轴上不同。当点击 Streamer 对象时，屏幕上会看到 Gizmo 显示当前的加载范围区域，见上图。

  • Use Loading Range Min（使用最小加载范围）复选框：勾选后即可使用 “Loading Range Min” 功能，称之为 Ring Streaming（环形流式）。这是全新的系统，允许在特定范围（“从 — 到”）内加载对象。如果对象太近会被移除，太远也会被移除。

  • Loading Range Min（最小加载范围，即环形流式）：一个按每个轴设置的整数值，指定要从 “Loading Range” 中挖掉的虚拟网格元素半径。Streamer 会加载这个环内的所有内容。如果（玩家）离得足够近，它就会把模型从内存中移除，或者干脆不加载它们。它用于用其他层的模型/对象替换近距离的模型/对象。当点击 Streamer 对象时，屏幕上会看到 Gizmo 显示当前的加载范围区域。看下图，从加载区域中挖掉了一块区域。

  • Sync with other layer（与其他层同步）：此选项在勾选 Loading Range Min 时出现。它同步两个层之间的加载和卸载，以避免任何空洞和流式加载问题。数据不会在另一层准备好替换它之前被卸载。

  • Deloading Range（卸载范围）：一个整数值，指定系统在此半径之后卸载虚拟网格元素（场景）。记住！ 虚拟网格元素要在在 “Destroy Tile Delay”（销毁瓦片延迟）中设置的时间过后才会被卸载——所以第一个标准是距离，然后才是时间。如果世界是循环的，卸载范围必须小于世界网格总数的一半减 1 个网格元素。

  • Position check（位置检查）：以秒为单位的位置刷新时间。Streamer 根据跟随对象 “Player/Camera” 在世界 XYZ 中的位置加载/卸载保存在虚拟网格元素（场景）中的世界。

  • Destroy tile delay（销毁瓦片延迟）：以秒为单位的数值/时间，用于指定虚拟网格元素（场景）在离开 “Loading Range” 之后、从 RAM 中卸载之前要等待的时间。当玩家在虚拟网格元素边界来回移动，或经常在相同网格元素之间移动时，这个值很有用——它帮避免短时间内的多次加载/卸载操作。它在 “Ring”（环形）流式中也很有用：旧模型会等待一段时间才被移除，在此期间下一层会用其他对象填满这个位置。

  • Max Parallel Scene Loading（最大并行场景加载）：一个整数值，让决定希望同时流式加载多少个虚拟网格元素（场景）。此选项对优化流式加载很有用。数值低会导致加载更慢，但不会有性能下降。必须估算并测试几个数值来适配需求。

  • Scene Load Wait Frames（场景加载等待帧数）：以帧为单位的数值，用于设置虚拟网格元素加载之间的延迟。建议在流式加载过程中留出几帧空余，这会让流式管线免于过载。如果流式加载的是很小的虚拟网格元素，可以设为 1 或 0。如果选择的时间太长，流式加载会仅仅因为空帧而变得非常慢。必须为需求估算并测试几个值。

  • Player（玩家）：这里放置代表流式系统玩家位置的对象。

  • Looping（循环）复选框：为该 Scene Collection 启用循环，这创造出一个无尽世界。每个 Streamer 及其场景集合是独立循环的。

    • 如果所有层的网格数量不同，请勾选 sync scene collection limits（同步场景集合边界），这将同步它们。
    • 如果世界不算巨大，并且允许同一场景被同时加载多次，只需勾选 override single instance scene（覆盖单实例场景）。在这种情况下，可以循环任何大小的世界。
    • 可以在特定距离值上强制循环——“Override X, Y, Z limits”（覆盖 X/Y/Z 边界）。例如，如果在 “Y” 轴上加载范围为 “0”，可以通过指定世界距离在 Y 轴上循环世界。

  • Spawned Player（后生成玩家）复选框：表示 Streamer 应该等待玩家在 Gameplay 场景中生成（spawn）。系统会等待带所选 “Player tag”（玩家标签）窗口标签的对象出现。如果启用此选项，请把每个 Streamer 中的 “player” 窗口以及其他使用玩家对象的脚本留空。

4.3 传送或重生（Teleport or Respawn）

把 _PlayerTeleport 预制体拖入 “Gameplay” 场景。玩家将被传送到与该预制体 XYZ 坐标相等的位置。把场景中使用的所有 Streamer 对象（来自层级）填入 Streamers 窗口。如果要在传送/重生时使用加载画面，请填写 “UI Loading Streamer” 窗口。如果要使用浮点修复系统，请填写 “World Mover” 窗口。下面是每个设置的信息，也会看到关于如何把重生/传送设置进游戏的图片。

  • UI Loading Streamer：这里可以把 UI Canvas 和加载画面连接到传送/重生系统。这让可以在玩家重生或传送后使用加载画面系统。只需把场景层级中包含 UI Loading Streamer 脚本的对象拖进此窗口。在预制体中，它是 “Streamer_GUI” 对象的子对象。
  • Streamers：这里应放入场景层级中拥有的所有 Streamer 对象。如果不止一个，增大数组尺寸并把它们全部拖进来。
  • World Mover：只有当使用浮点修复系统时，才用场景层级中的 World Mover 对象（包含 world mover 脚本的对象）填写此窗口。
  • Player：这里拖放场景层级中代表流式系统玩家位置的对象。这个对象会在重生/传送过程中被移动。
  • Player Mover：如果在加载/传送期间使用安全位置系统，拖放场景层级中包含 player mover 脚本的对象。在预制体中，_Safe_Place_Spawn_and_Teleport 包含此脚本。

如果想使用传送按钮，只需把 LevelReset_Teleport_button 预制体和 EventSystem 预制体拖入场景。在 “On Click” 窗口中填入场景层级中的 _PlayerTeleport 对象。选择按钮功能 PlayerTeleport → Teleport(bool)。按钮和事件系统也已附加到 “Streamer_GUI” 预制体上。看下图。

开始时可以使用简单的加载画面系统。它包含加载进度条，应用起来很容易。也可以使用脚本构建自己的加载画面系统，并连接到 World Streamer。

  • Streamers：这里应放入场景层级中拥有的所有 Streamer 对象。在这里只拖入应该影响加载画面的那些 Streamer。如果不止一个，增大数组尺寸并全部拖入。
  • Wait frame（等待帧）：一个以秒为单位的非常重要的值，应大于 1~2。这是加载画面系统获取信息所需的时间——了解所有 Streamer 中有多少个虚拟网格元素（场景）会影响加载画面。如果太短，加载画面可能在所有虚拟网格元素（场景）加载完成前就结束；但如果太长，只是浪费时间。可能大约 2~3 秒比较合适。
  • Progress Img（进度图片）：如果此窗口没有自动填入，或想更换，就在这里拖入进度条图片。

4.5 浮点修复系统（Floating Point Fix System）

如果游戏区域太大，或者使用了循环（looping）系统，就应该使用浮点修复系统。简单来说：当引擎中的坐标变得过大时，物理系统以及所有基于对象位置的 Unity 系统都会开始出现计算精度下降。这可能导致物理系统出现异常状况，并产生图形错误，比如阴影闪烁。

正因如此，创建了这套系统来消除这个问题。World Mover 会时不时地重置世界的坐标位置。这里说"时间”，实际指的是以虚拟网格元素（场景）间隔来表示的一段距离。之所以用"瓦片数量/间隔"而不是 XYZ 距离，是因为对整个系统来说，用它来判断"何时该重置"更简单、更清晰。不应该过于频繁地重置世界坐标，因为对大多数游戏来说，这是一个开销很大的操作。浮点修复系统还包含支持多人游戏的解决方案，所以请留意 **“Current Move”（当前偏移）**这一位置参数。

浮点修复系统和循环不支持：

  • Static batching（静态合批）——因为目前无法移动这些静态合批对象（Unity 会阻止）。可以使用自定义合批系统，或通过手动合并网格来合批对象，也可以使用 Asset Store 上可用的工具。 Unity Terrain 应保持勾选静态合批，仍然能够移动这些已合批的地形。

要为游戏添加浮点修复系统，只需把 _World_Mover 预制体拖入场景，并填写所有必要的信息。如果使用传送/重生系统，请查看下面的 “Important1” 说明。如果相机与玩家分离，或存在一些需要与玩家一起重置位置的对象——如：相机、单人游戏中的 AI、天气或天空盒/地平线对象（它们不是由 Streamer 流式加载的，但需要保持与玩家位置的相对关系）——请查看下面的 “Important2” 说明。

  • XYZ Tile Range（XYZ 瓦片范围）：用于设置在多少个虚拟网格元素之后系统会重置坐标。例如，如果 tile range 是 “1”，主 Streamer 的每个虚拟网格元素尺寸是 200×200 单位，Streamer 会在经过 2 个虚拟网格元素后（从 0 开始计数）把玩家和整个世界设为 0,0,0 位置。这意味着移动 400 单位后，每经过 400 单位系统就会重置一次整个世界的位置。
  • Streamer Main（主 Streamer）：在这里选择由哪个 Streamer 决定系统多久重置一次世界坐标，以及由哪个虚拟网格（来自哪个 Streamer）决定重置何时发生。建议使用拥有最大虚拟网格元素的 Streamer；如果流式加载 Unity Terrain，应该使用包含 Terrain 的那个 Streamer。
  • Streamers Additional（附加 Streamers）：在这里放入场景层级中所有剩余的 Streamer，它们应受浮点系统影响。99% 的情况下，应该把它们全部拖进来。
  • Current Move（当前偏移）：玩家的真实位置与本地位置之间的差值，对校正与服务器的 RPC 通信或校正从代码生成（spawn）的对象很有用。本地玩家位置 − Current Move = 真实玩家位置。本地玩家位置是玩家游戏对象当前的实际位置，它已被重置过几次，所以称它为"本地”。

Important1（重要说明1）！ 如果使用传送/重生系统，必须把场景层级中的 _World_Mover 对象连接到同样是场景层级中的 _PlayerTeleport 预制体上。只需把层级中的 _World_Mover 对象拖到 _PlayerTeleport 脚本的 “World Mover” 窗口中。

Important2（重要说明2）！ 对于跟随玩家或与玩家/世界保持重要关系的对象，有 “Object to Move”（待移动对象）脚本。只需把该脚本附加到应在位置重置期间跟随玩家/世界的对象上，这样玩家与这些对象之间的相对关系就会保持不变。

如果有跟随玩家或对象的粒子，请把它们的 Simulation Space（模拟空间）改为 Local（局部）；如果无法做到，就只在位置重置的那一刻切换。如果不更改这个，粒子会有一个小断裂，因为它们需要在新位置重新生成。

4.6 如何循环整个世界或特定对象/模型

World Streamer 可以让循环整个世界，或者模拟一颗星球。也就是说，世界可以是无边无际的。循环功能也可以用于可重复出现的事物，比如太空中的小行星。

要循环世界，只需在场景层级中勾选 Streamer 上的 “Looping”（循环）复选框。循环世界应该配合浮点修复系统使用，因此还需要完成 “4.5 浮点修复系统"一节中列出的全部设置。

Looping（循环）复选框：为该 Scene Collection 启用循环，这创造出一个无尽世界。每个 Streamer 及其场景集合是独立循环的——这意味着如果想同步它们，它们必须有相同的世界尺寸，或者只需勾选同步复选框（sync scene collection limits）。还可以通过距离强制世界循环——使用 Override X, Y, Z limits（覆盖 X/Y/Z 边界），例如当某个轴上没有数据时。

一个层可以与其他层有不同的循环范围——例如，如果取消勾选 sync scene collection limits，小镇层可以比整个世界循环得更频繁。

由于在循环过程中会移动世界对象，循环系统与浮点修复系统具有相同的限制。

浮点修复系统和循环不支持：

  • Static batching（静态合批）——因为目前无法移动这些静态合批对象（Unity 会阻止）。可以使用自定义合批系统，或通过手动合并网格来合批对象，也可以使用 Asset Store 上可用的工具。 Unity Terrain 应保持勾选静态合批，仍然能够移动这些已合批的地形。

4.7 环形流式（Ring Streaming）理念

这套系统允许在一个特定范围（“从 — 到”）内加载对象。称之为"环形流式”，因为流式加载的区域看起来像一个环——对象离得太近会被移除，离得太远同样会被移除。

环形流式可以用于在近距离或远距离替换对象。例如：第一个 Streamer 只在近距离流式加载高精度、高细节的对象/Terrain 层；第二个 Streamer 只在远距离流式加载低质量的对象/Terrain。低质量对象/Terrain 会在高质量对象/Terrain 加载的位置处消失。这样就能获得极佳性能的远景。如果某个对象——比如 Unity Terrain——不支持 LOD 系统，而且它的数据（无论是否可见）加载起来非常沉重，那么这就是一个非常好的解决方案。

开启方法：在场景层级中选中 Streamer 对象，勾选 “Use Loading Range Min”，并勾选 “Sync with other layer”，然后填写 “Loading Range Min” 的数值，并选择要与之同步的那一层。

  • Use Loading Range Min（使用最小加载范围）复选框：勾选后即可使用 “Loading Range Min” 功能，也就是所说的环形流式。
  • Sync with other layer（与其他层同步）：允许在两个层之间同步流式加载，这样数据不会在同步层准备好替换它之前被卸载。
  • Loading Range Min（最小加载范围，即环形流式）：一个按每个轴设置的整数值，指定要从加载范围中挖掉的虚拟网格元素半径。Streamer 会加载环内的所有内容。如果（玩家）离得足够近，它会把对象从内存中移除，或者干脆不加载它们。它用于用其他层的对象替换近距离的对象。当点击 Streamer 对象时，屏幕上会看到 Gizmo 显示当前的加载范围区域，如上面图示。

4.8 物理管理器（Physics Manager）

如果场景或流式世界中包含物理对象，而希望防止它们因为周围环境被移除/卸载而坠落或移动，只需在每个物理对象上添加 “Physic Culling System”（物理剔除系统）脚本即可。当玩家离得太远时，系统会保持（冻结）对象并保存其速度/方向向量；当玩家回到指定区域时，系统会读取保存的速度/方向向量，对象就会恢复自然的行为表现。Physic Distance（物理距离）——一旦越过这个距离，对象就会被冻结。可以在预制体目录中找到 _PhysicCulling_Test 预制体，它会帮助理解这套系统的工作原理。

4.9 地形剔除系统（Terrain Culling System）

这套系统会在 Unity Terrain不在相机视野内或离玩家太远时将其隐藏起来。“Terrain Culling System” 脚本必须添加到每一个地形分块上，最好在切分过程中批量添加。系统与主游戏相机联动，因此地形在场景视图中也可以被隐藏。它能节省 CPU 开销，因为不可见的树和地形部分不会被刷新它们的树木和 LOD。系统通过 “MainCamera” 标签识别主相机，并使用它的视锥来判断剔除或显示地形对象。

4.10 数据加载期间玩家处于安全位置

如果想把玩家移动到安全位置，直到加载/传送结束，把 _Safe_Place_Spawn_and_Teleport 预制体拖入 Gameplay 场景层级。这个系统也支持后生成的玩家（spawned player）。需要填写：

  • “Streamers” 列表：填入 Gameplay 场景中应影响安全位置系统的 Streamer。
  • “Safe Position”（安全位置）：一个带位置的对象，玩家会被移动到那里，直到系统读取完所选 Streamer 的数据。
  • “Player”（玩家）：把应被移动的玩家拖到这里。如果玩家是后生成的，系统会接管此事，所以把这个位置留空即可。玩家生成后会立即在安全位置等待游戏开始。

如果想在传送期间使用这个系统，还必须在 _PlayerTeleport 对象的 “player mover” 窗口中填入场景层级中的 _Safe_Place_Spawn_and_Teleport 对象。

5. Terrain Streaming 完整流程

首先，在开始流式加载的地形之前，有几件事需要说明。如果要流式加载 Unity Terrain，它必须被切成多个部分。每个 Unity Terrain 部分都会产生静态的 CPU 开销，而在加载下一个瓦片时还会产生动态开销。所有这些性能消耗都可以被解决或降低——具体方法见 《Unity Terrain 的大量细节与性能解决方案》一节。在系统中，Terrain 可以循环，也可以在远距离被低多边形网格替换。请仔细阅读《地形流式加载》一节中给出的全部信息，它能为节省大量时间，并确保相对任何其他可用方案都极其出色的性能。

5.1 地形准备——Unity Terrain、低多边形网格生成

要流式加载的地形，需要先为这个过程做好准备。

1. 概念

当开始流式加载 Unity Terrain 时，需要把 Terrain 切成多个部分/分块。在 Tools → Nature Manufacture → World Streamer → Scene Manager → Terrain Manager 部分，可以切割地形、估算地形尺寸，并为远景生成低多边形版本。记住：保留的源地形不动！ 因为可能会改变主意、调整虚拟网格元素的大小，然后测试它在更大或更小分块下的表现。

也可以先用 Unity 现成的地形系统按瓦片生成的世界，再用工具处理它——比如为远景生成低多边形网格。

开发者们总是问：地形分块应该多大？ 基本上这由决定，不过根据选择的不同方案，可以给出一些建议：

  • (a) 如果不想使用环形流式，也不想在远景用低模网格替换 Unity Terrain，那么的每个地形瓦片尺寸应为相机远裁剪面的 110%。这能保证较低的静态 CPU 开销，因为可以把加载范围设为 1，只加载 9 个地形瓦片。这么大的瓦片也意味着相当大的内存消耗（但还不算严重），以及因剔除（大量树对象）产生的相当大的 CPU 消耗。建议 110% 的原因是：没有人想看到地形加载（出现）的过程，这种情况偶尔会发生。留出这 10% 的"时间"给加载过程，就不会穿帮。

  • (b) 如果用环形流式把远处的地形替换为低模网格（这是好得多的方案），那么的地形分块/部分应为相机远裁剪面的 10%~50%。10% 适合想通过游戏内选项来控制地形细节、且低模网格中烘焙了树（如示例）的情况；30%~50% 适合只想保持地形原样的情况。这个方案的优点是：可以获得非常远的视野，而每个低模地形网格只消耗少量顶点/三角形和 1 个 drawcall。可以承载很多地形瓦片，因为它们大多是简单网格，而 Unity Terrain 本身很小、数据量少、刷新时间短。通过 Streamer 的加载范围（loading range）和最小加载范围（loading range min），可以调整地形在什么距离变成低模网格。这是一个动态选项，可以在游戏过程中更改——玩家可以选择细节等级。

  • (c) 如果只用低模网格代替 Unity Terrain（可能用于手机游戏），可以使用任意尺寸，但记住要让瓦片数量与相机远裁剪面匹配。最好保持已加载瓦片的数量与尺寸为相机远裁剪面的 110% 左右，只是为了地形出现/显示时不穿帮——留出这 10% 的"时间"用于加载新瓦片。

自定义地形方案总是比较困难，因为没有测试过所有方案，所以它们很可能是本节 (b) 和 (c) 两种方式的组合。

2 地形准备

  1. 要为流式加载准备地形，有几步操作。第一步是打开 Terrain Manager。
  2. 设置切分后地形应具有的选项：如 draw instanced、pixel error、草和树的设置、风等。
  3. 选择地形切分的次数。2 意味着地形在 X 和 Z 轴上各切一刀，会得到 4 个瓦片，以此类推。点击 Split，系统会把地形切成多个部分。
  4. 如果想获得最佳性能，应该从地形和树生成低模网格。在环形流式中，它们会替换沉重的地形数据，且没有可见影响。这将大幅减少 drawcall 和三角形数量。在这里可以设置几项：
    • Terrain LOD = 3：低模地形不需要更密集的形状，设为 4 很可能损失太多形状细节。
    • Basemap resolution 设为 512：远景更高的纹理分辨率基本没用，只会占内存。1024 大概也是合理上限。
    • Normal details 和 strength：按 Unity Terrain 估算的默认值，随时可以调整。
    • 如果使用 NM 树或最后一 LOD 为 cross 面片模型（不是 billboard）的树，可以选择较大的树一起烘焙进地形。尽量避免把小树放进去——它们很快会看不见，不值得放进远景。这样可以避免"树因 LOD 剔除距离消失、又在低模网格里出现"的情况。不要在远景添加不必要的数据，直接取消较小树的复选框即可。

4 第一个地形的起始位置 XYZ 必须是完整取整的数值，比如：5000、-5000、0、1000、500、-100 等，而不能是 99.98、0.1、-0.018 这种。这种错误位置会导致虚拟网格元素中出现意料之外的地形偏移。记住：虚拟网格元素从 (0,0,0) 开始，而 Unity Terrain 的 pivot 位于它的角落，这有时会导致地形与虚拟网格边界之间产生偏移。可以通过把地形放在其尺寸的整数倍位置上来消除偏移。例如：地形瓦片尺寸是 500×500，虚拟网格元素尺寸是 500×500，那么地形对象必须位于 500、0、-500、1000、-1000 以及 500 的其他整数倍位置上。这样就能让虚拟网格元素与地形完全对齐。

5 重命名地形对象：在名称开头添加 “LOD0_Terrain”（高清地形），低模地形网格则加 “LOD1_Terrain”。当然这可以是任意词，只是举例。这个词会在切分/归类过程中被使用，用于把地形放入正确的虚拟网格元素和层中。也可以始终使用 “Object Parent” 脚本，把地形放在父游戏对象下，这样就不需要任何命名规范和对象前缀。

6 从这些地形创建预制体：这不是必须的，但它让无需打开场景就能访问它们，所以很实用。可以在确定地形分块尺寸适合的游戏之后再创建预制体——很可能要在看到流式效果之后才会确定。

  2. 将 _Streamer_GUI 预制体拖入的游戏场景。这个预制体包含图形 UI、加载画面、传送/重生功能，以及用于浮点修复或循环系统的 “Position”（位置）Gizmo 查看器。

  • Loading Range（加载范围）：X = 1，Y = 0，Z = 1
  • Use Loading Range Min（使用最小加载范围）：false（关闭）
  • Deloading Range（卸载范围）：X = 1，Y = 0，Z = 1
  • Destroy Tile Delay（销毁瓦片延迟）：2 秒
  • Position Check Time（位置检查时间）：0.1 秒
  • Max Parallel Scene Loading（最大并行场景加载）：1
  • Scene Loading Wait Frames（场景加载等待帧数）：2 帧
  • 把场景层级中的玩家拖入 “Player” 窗口。系统会跟随该玩家，在玩家靠近时加载地形瓦片。
  • 对于生成的低模网格，设置 Loading Range Min = 1（环形流式），Loading Range 和 Deloading Range = 6。

总结一下这些设置的含义：

将加载 3×3 区域的地形部分/虚拟网格元素/场景，并卸载超出此范围的每一个虚拟网格元素。每 0.1 秒检查一次玩家位置。Streamer 每帧最多加载 1 个地形部分，并在每个虚拟网格元素加载完成后、加载下一个之前，留出 2 帧空余让异步流式操作完成。

  1. 如果想使用加载画面，现在来设置 UI：

  • 然后把场景层级中的 _Streamer 拖入 “UI Loading Streamer Script” 的 element 0 位置。Element 0 承载的是高质量地形。加载画面中的进度条只有在 element 0 的所有场景全部加载完成后，才会放行玩家进入游戏。

Important2（重要说明2）： 当修改地形（添加植被、改变形状、绘制纹理）时，不必重新切分场景、也不必刷新 Streamer。地形保存在场景中，场景持有对地形数据的引用，也就是说所有内容始终是最新的。

5.4 Unity Terrain 的大量细节与性能解决方案

流式加载并持有大量细节的地形而不用大量占用 CPU，是可能的！

  • 可以使用环形流式——低模地形甚至可以包含烘焙进去的树。远景植被和地形在这种配置下只占少量批次和三角形。看看巨大世界 Demo。
  • 关闭不可见地形的渲染——用自己的方案或 “TerrainCullingSystem” 脚本。只需把它拖到每个地形预制体/对象上，并为该地形设置最大可见距离。
  • 两种方案都上：环形流式 + 脚本剔除。
  • Vegetation Studio 或 Vegetation Studio Pro——移除整个植被，把它移入间接实例化（instanced indirect）。这样地形只包含高度图和纹理。它还支持其他产品中制作的自定义 shader。
    • https://assetstore.unity.com/packages/tools/terrain/vegetation-studio-103389
    • https://assetstore.unity.com/packages/tools/terrain/vegetation-studio-pro-131835

这些建议能大幅降低静态地形的 CPU 和内存占用！使用这个方案，甚至可以在移动设备上渲染非常远的地形视野！

如果在场景中留下的对象（精细地形）数量很少，某些脚本可以运行得更快。当调用垃圾回收器（GC）时，它的尖峰会降低到可以忽略的程度。如果想从内存中移除对象，必须时不时调用 GC——系统会调用它，随时可以在代码中更改调用频率。

如果纹理流式加载很慢/产生尖峰，请调整 Quality 设置中的 “Async Upload Time Slice”（异步上传时间片） 和 “Async Upload Buffer Size”（异步上传缓冲区大小）。

记住在 Player Settings 中使用 incremental GC（增量 GC），这会大幅加快 GC。

所以总结一下：可以对近距离使用 Unity Terrain，并关闭相机看不见的地形（智能剔除脚本）；对远距离，可以使用带烘焙树、自定义树木系统或不带树的低模网格。在这种设置下，可以移除数百万个顶点和数千个 drawcall。加载会很流畅，不会影响玩家的 CPU。内存占用会非常低——可能会削减几百 MB，可以把它们花在纹理和模型上。听起来很诱人，不是吗？确实是——这正是主机游戏和 MMO、AAA 游戏处理地形和模型的方式。

6. 模型/对象流式加载（Model/Objects Streaming）

模型和对象流式加载是 World Streamer 的主要功能。 借助方案，能够从磁盘读取那些已被放置在世界中、并由切分工具切分成虚拟网格和层的对象。切分系统可以轻松地刷新、增长、缩减世界库（虚拟网格元素/场景）。可以放入大量不同类型的对象：灯光、粒子、模型、碰撞体、反射探针——一切都会在正确的时机从磁盘读取。

强烈建议按层流式加载对象/模型。这让获得更好的性能，并能优化一些 Unity LOD 系统不支持的功能。当然，一切都兼容 Unity LOD 系统，但提供得更多。如果在场景中留下的对象数量很少，某些脚本可以运行得更快。当调用垃圾回收器（GC）时，它的尖峰会降低到可以忽略的程度。如果想从内存中移除对象，必须时不时调用 GC。

所说的优化尤其涉及粒子和灯光。可能已经注意到：如果把灯光或粒子放入 Unity LOD 系统，当它们被剔除（culled）后：

  • 灯光仍然是激活的，仍在发光，并在它照到的对象上增加 drawcall。
  • 粒子仍在 CPU 上运行。如果查看 Profiler，粒子仍然占用 CPU，因为更新和生成过程仍在进行。

所有这些 CPU、RAM、VRAM、GPU 占用都可以被 World Streamer 移除。灯光和粒子只有在它们足够接近、即将可见时才消耗资源。

如果纹理流式加载很慢/产生尖峰（报 “GFX wait for present”），请调整 Quality 设置中的 “Async Upload Time Slice” 和 “Async Upload Buffer Size”。

让回到对象和流式加载。这个小教程将帮助在游戏过程中流式加载对象。会有很多文字（可能已经看到了），但一切必须讲清楚。完成本教程后，将能够非常快速地处理/刷新/添加/移除流式模型/对象。

6.1 模型/对象准备

总是建议打开/创建一个空场景，称之为 “Work” 场景，把全部内容（想要流式加载的）复制进去。方向光、玩家、UI 应放在游戏场景，所以把它们从这个场景移除，或在切分过程中隐藏。如果正确设置了层，这些对象也可以留在原处。

  1. ** 思考希望把对象流式加载到多少个层中。** 一切都取决于游戏风格。以 GTA 风格的游戏为例——这有助于把层和流式加载理念可视化。建议使用这样的架构：
  • Big objects（大对象）——它们的轮廓从远处就能看到（建筑、道路、巨大岩石结构）。
  • Medium objects（中对象）——相当大、需要在较远距离看到的重要对象（静态车辆、建筑附属物、栅栏、灯笼、灌木、箱子、路牌）。
  • Small objects（小对象）——真正很小、不重要、细节性的对象（纸张、泥土、街道井盖、花朵、垃圾、垃圾箱、小路牌）。
  • Lights and Particles（灯光和粒子）——可以把它们放进中对象或小对象层，也可以为它们单独创建一层。

如果做的是 RTS 或俯视角游戏，可能只需要一层，或少于上面列表的层数。对于太空游戏，应该把星星、行星、小行星等分开……简单来说，应该按尺寸和可见距离对对象编目。无论如何，层数是自己的独立选择。

  1. 决定使用多少层之后，应该通过在对象名称开头添加一个额外单词来重命名场景中的对象。在后续文档中称之为前缀（prefix）。应该从重命名预制体开始。当在项目中重命名预制体时，场景层级中的对象通常也会自动重命名。看示例：
  • 示例 1：Big_Objects_Building（建筑）
  • 示例 2：Medium_Objects_Fence（栅栏）
  • 示例 3：Small_Objects_Flower（花）

这些名称在自动归类过程中很有用。重命名的资源会为节省大量时间，让能随意摆放模型，而不用思考它们属于哪一层。

不必重命名对象——可以使用父级游戏对象，按类别把模型放进去。例如：所有建筑放进 “Big objects”，所有中等尺寸对象放进 “Medium Objects” 等。如果放入 “Object Parent” 脚本并设置正确的前缀（如 “Big_Objects_Building”），系统会直接从正确的父级取对象进入正确的层，忽略内部对象的名称。对大多数用户来说这可能更快，但它迫使在层级中保持秩序。

如果打算把所有东西在一个层中流式加载，那就忘了重命名吧，不需要它。

  1. 把模型从所有母文件夹中解包（unpack）——如这个画面所示；或使用 “Object_Parent” 脚本，就像 “Tutorial World Streamer - Advanced_Work_Scene_Catalogs” 演示场景那样。

如果想作为一个整体（连同母/父对象一起）流式加载子模型和预制体，就让它们保持原样。如果决定把建筑细节与建筑整体轮廓分开、以更短的距离流式加载，那么也应该把它们从建筑中解包。如果不这样，总是可以把它们留作 LOD。如果细节是建筑预制体的一部分，LOD 可能更聪明——但这意味着把它们留在 GC 列表里，也就是说决定在场景中保留不必要的对象，数量多了会对垃圾回收器（GC）造成压力。

  1. 完成。现在是切分、分层和流式加载的时间了。

6.2 场景切分与虚拟网格设置

当对象按照 “6.1 模型/对象准备"一节准备好后，就可以切分它们了——这意味着将把它们自动放入正确的虚拟网格元素和层中。继续 6.1 节开始的示例。现在按以下步骤操作：

  1. 点击 World Streamer → Scene Splitter 打开 “Scene Manager” 窗口。
  2. 填写 Scene Splitter 窗口：
  • Add Layer（添加层）
  • 勾选 “Split X” 和 “Split Z”；如果 Y 轴对流式不重要（像太空游戏那样）就不要勾 “Split Y”。如果不想因为玩家 Y 位置而移除模型，也不要勾 “Split Y”。对于 “Small_Objects”、“Medium_Objects” 层，“Split Y” 轴可能有用。
  • 填写 X、Z 尺寸，Y 可选。把它们与对象尺寸和密度对照。不要把 100×100 单位的对象放进 10×10 的虚拟网格元素尺寸。模型流式加载非常非常高效，尤其是在构建模式下。在编辑器里可能慢，因为运行时合批和碰撞烘焙——别担心，构建中没有这些。可以一次流式加载许多建筑，所以开始时也许可以试试 “X size” 300、“Z size” 300 单位。随时可以更改，几秒钟后就有新配置可以运行时测试。
    • 要考虑的是：如果希望从 1500 单位距离看到建筑：1500（最大视距）/ 300（虚拟网格元素尺寸）= 5。就需要把流式距离（Streamer 对象上的加载范围）设为 300×5 = 1500。
  • 填写 GameObject Prefix 为添加的识别大对象的词，即 “Big_Objects”。Splitter 会检查场景中所有对象，如果任何对象名称以 “Big_Objects” 开头，就会在层中使用它。
  • 填写 Scene Prefix（层名） 为对来说清晰的名字，可以与该层同名，如：“Far_View”；如果有多个世界，也可以添加它属于哪个世界的信息。带此信息的名称看起来像：“World_1_Far_view”。
  • 对想要创建的其余层做同样的操作。如果只有一层，跳过此点：
    • “Medium_View” 给包含 “Medium_Objects” 前缀的对象
    • “Short_View” 给包含 “Small_Objects” 前缀的对象
    • 可以为每层更改虚拟网格元素尺寸，或保持相同。
  • 重要：场景/虚拟网格元素没有数量限制，但如果创建太小的虚拟网格元素，drawcall 数量会增加，而且流式加载会更慢——仅仅因为有太多部分要加载/卸载。不要创建太大的虚拟网格元素，因为会在内存和垃圾回收器中持有许多不必要的资源，这可能导致更大的 GC 尖峰。应该通过几次测试来估算虚拟网格尺寸，这只需要几分钟。

  1. 如果对 Scene Manager 窗口中填的一切有把握，可以为每层单独点击 “S” 按钮，或点击 “Split Scene”（影响所有层）。可以用 “C” 按钮撤销特定层的操作，或用 “Clear Scene Split” 撤销所有层。切分过程中，系统会从选择的资源准备虚拟网格元素。虚拟网格元素将来会变成场景（下一步）。更多信息见 “4.1 Scene Splitter"一节。

  2. 如果对系统生成的虚拟网格元素有把握，点击 “Generate Scenes from Virtual Grid”（从虚拟网格生成场景）。这是对资源要做的最后一步。系统会开始从虚拟网格元素生成场景，在指定目录（或默认目录）中创建场景。系统还会创建场景集合预制体。在示例中，会得到名为：Scene_World_1_Far_View 或 Scene_Far_view、Scene_World_1_Medium_View 或 Scene_Medium_view 等场景集合预制体。

【图】这个场景集合预制体将存储在生成场景的目录中。在示例中：WorldStreamer → SplitScenes →（Scene_World_1_Far_View 或 Scene_Far_view；Scene_World_1_Medium_View 或 Scene_Medium_view 等）

  1. 这些文件（场景集合）包含关于场景的全部最新信息：共有多少个、如何切分的、从哪里开始到哪里结束（位置）。这些重要的场景集合预制体将被连接到 “Gameplay” 场景中的 Streamer 对象上。它让系统能够在正确的时间和位置流式加载全部内容。

6.3 游戏场景中的 Streamer 设置

当 “6.2 场景切分与虚拟网格设置"一节的所有工作完成、有了场景集合（或集合们——如果做了几层），就可以开始设置 “Gameplay” 场景了。打开已有的 “Gameplay” 场景，或创建一个。将在下面为每一层做所有要点。逐步来：

  1. 打开 “Gameplay” 场景——这是拥有玩家、方向光和相机的地方。
  2. 把 “Streamer” 预制体拖入游戏场景层级——但如果也使用地形流式加载，应该使用现有的 Streamer，只需添加另一层/场景集合。
  3. 如果要使用加载画面，把 _Streamer_GUI 或 _Loading_Screen_UI 预制体拖入游戏场景层级。仅当场景中还没有 _Streamer_GUI 或 _Loading_Screen_UI 时才这样做。 这个预制体包含图形 UI、加载画面、传送/重生，以及用于浮点修复或循环系统的 “Position” Gizmo 查看器。如果这是第二层或后续层，不需要做这一步——不想重复 UI。
  4. 点击层级中的 “Streamer”。把从 “6.2” 节制作的场景集合拖入 “Scene Collection” 窗口。通过这一步，把生成的场景与 Streamer 连接起来了。
  5. 按照 “4.2 Streamer 对象"一节的知识填写 Streamer 设置。本手册示例将设置如下：
  • Loading Range：X = 5，Y = 0，Z = 5（针对必须从 1500 单位外可见的建筑，每个虚拟网格元素 300×300 单位：300×5 = 1500 单位）
  • Use Loading Range Min：false（关闭）
  • Deloading Range：X = 5，Y = 0，Z = 5
  • Destroy Tile Delay：1 秒
  • Position Check Time：0.1 秒
  • Max Parallel Scene Loading：1
  • Looping：false（关闭）
  • Scene Loading Wait Frames：1 或 2 帧

总结这些设置的含义：将加载 5×5 区域的虚拟网格元素（场景），每个虚拟网格元素是 300×300，并卸载超出此范围的每一个虚拟网格元素。每 0.1 秒检查一次位置。每帧最多加载 1 个虚拟网格元素，并在每个虚拟网格元素加载完成后、加载下一个之前，留出 1~2 帧让异步流式操作完成。

  • 把场景层级中的玩家拖入 “Player” 窗口。系统会跟随该玩家，在玩家靠近时加载地形瓦片。
  1. 现在填写 UI——当然，只有当想使用加载画面时才需要。
  • 点击场景层级中 “Streamer_GUI” 下的 _Loading_Screen_UI 对象，在 Streamer 值里填写 Size = 1（如果 Streamer 更多则填更大值）。可以在 “UI Loading Streamer Script” 中找到这个值。
  • 然后把场景层级中的 “Streamer” 拖入 “UI Loading Streamer Script” 的 element 0 位置。如果想在加载画面中使用其余的 Streamer，也请把它们拖进这个窗口。
  1. 现在点击场景中的 “Streamer” 和每个 Streamer 预制体——如果还没有把场景集合中的场景加入 Build Settings，会看到一个带按钮的警告。点击它，系统会自动把缺失的场景加入 Build Settings，或刷新它们。每次改变虚拟网格元素的数量和尺寸，都必须点击这个按钮！
  2. 点击 Play，大功告成！

Important（重要说明）！ 现在可以轻松地切分/取消切分/添加新对象/移除内容/移动内容，并在 Work 场景中点击 Split 再重新生成（或使用 “Local Area Updater”），几秒钟内就能刷新对象层和流式世界。系统会刷新场景和游戏场景中的 “Streamer”。只需要点击 “Add to Build Settings” 按钮刷新它们。这意味着可以轻松测试很多种配置！

7. 通过碰撞体流式加载（Streaming by Colliders）

碰撞体流式加载对加载/卸载/剔除室内、房间、楼层非常有用，也可以只在玩家/对象撞到碰撞体时才加载某些东西。这个功能能为节省大量 CPU/GPU/RAM/VRAM 占用——可以用室内内容填满整座城市，只在玩家撞到门或靠近相应区域时才加载它们。使用起来非常简单快捷。

7.1 对象准备、切分与场景生成

这很简单。让一步步来：

  1. 在想通过碰撞体流式加载的对象附近创建一个空游戏对象，把它命名为 Collider_Stream_Interior_1（碰撞体流式_室内_1）。

  2. 给这个游戏对象附加碰撞体（Collider），并勾选 “Is Trigger”（触发器）。

  3. 调整碰撞体尺寸，使其覆盖"流式对象应被加载并驻留内存"的区域。

  4. 把想流式加载的对象移入 Collider_Stream_Interior_1 对象中，让它们成为它在场景层级中的子物体。

  5. 给 _Interior_1 附加 ColliderScene 对象。

  6. 完成以上所有步骤后，情况应如下图所示：

【图】

  1. 打开 Scene Manager 窗口。

  2. 点击 “Generate Scenes from Colliders Only”（仅从碰撞体生成场景） 按钮。

  3. 生成过程：刚刚生成了 Collider_Stream_Interior_1 场景和带碰撞体的预制体 Collider_Stream_Interior_1_stream。可以在 WorldStreamer → SplitScenes → ColliderScenes 目录中找到它们。预制体包含与生成场景的连接，并保存原始对象位置。如果把这个预制体从项目窗口移动到任何其他场景的层级中，对象会位于与生成时相同的世界位置。当然，也可以更改预制体和生成位置。

  • 重要！！！ 系统允许把由碰撞体流式加载的对象隐藏在由场景集合（虚拟网格）Streamer 流式加载的场景中。这看起来像一个小套娃——场景再流式加载场景，等等。只需把它们放进任意层，在生成过程中系统会识别到"它找到了由碰撞体流式加载的对象”。它会为这些对象创建场景，并放入正确的位置。唯一要做的是通过 Scene Manager → BuildSettings → "Add scenes to build settings" 按钮把它们加入 Build Settings。生成场景后，这个窗口应该会自动填入正确的对象。

这个结构的另一个优势是：如果放置碰撞体流式对象的层是循环的且使用了浮点修复，碰撞体流式对象会与该层同步。对象会正确跟随世界和玩家。

如果只在项目中使用这种结构，不必经历 “7.2 游戏场景中的碰撞体 Streamer 设置"一节。只需要做这一节中的一件事：把项目中的 _Collider_Streamer_Manager 拖入 “Gameplay” 场景层级。这个预制体必须有 “ColliderStreamerManager” 标签——检查它！ 用场景层级中的玩家对象填充它。

7.2 游戏场景中的碰撞体 Streamer 设置

这比生成容易得多。

  1. 打开 “Gameplay” 场景。
  2. 把项目中的 _Collider_Streamer_Manager 拖入场景层级。这个预制体必须有 “ColliderStreamerManager” 标签——检查它！ 用场景层级中的玩家对象填充它。
  3. 设置应触发流式加载的对象标签（被撞击后）——例如玩家或主相机。这个玩家或相机对象必须有带 Rigidbody 的碰撞体才能触发流式加载。大多数情况下，开启 Kinematic（运动学）、关闭 Gravity（重力） 比较好。
  4. 只需把生成的预制体 Collider_Stream_Interior_1_stream 从项目窗口移动（拖入）到场景层级窗口。
  5. 点击 Add to Build Settings 按钮。如果忘了这一步，场景将无法加载。
  6. 决定是否只允许玩家在撞击时触发流式加载——通过勾选 “Player Only Activate”（仅玩家激活） 来决定。
  7. 设置 Unload Timer（卸载计时器）。经过这段时间后场景会被卸载，但这只会在流式触发者离开碰撞体区域后发生。
  8. 点击 PLAY，移动玩家/对象去撞碰撞体。对象会被加载。

8. 多层流式加载——为什么需要它

在 《6.模型/对象流式加载》和 《5.地形流式加载》章节中对层投入了大量笔墨。一切都关乎性能。

理念是：在游戏中保持尽可能少的对象数量。 如果在场景中留下的对象数量很少，某些脚本可以运行得更快。当调用垃圾回收器时，它的尖峰会降低到可以忽略的程度。如果想从内存/CPU 中移除对象，必须时不时调用 GC。也可以从另一个角度看：如果 GC 仍然太重，有了层，就不必那么频繁地调用它。

层让能够只持有当前真正需要的资源。小对象在足够远时会被从内存和 CPU（以及 GC 列表）中移除。让能够在远处持有大轮廓（如建筑、地形），同时享受只在近距消耗资源的大量细节。

带环形流式的层让能够把精细而沉重的 Unity Terrain 替换为低模网格。Unity LOD 系统不支持这种结构。进一步说：在这种结构中，如果没必要，根本不会在内存中持有/加载 LOD0。这不一定非要是地形——觉得在远处用静态 billboard 网格替换粒子怎么样？用 Unity LOD，即使切换到 billboard，粒子仍然会消耗 CPU。有大量粒子源时，可以通过环形流式节省很多。

层可用于分离以下对象：灯光、FX、模型、AI。它们分离后，不同专长的多位开发者可以在同一区域工作，互不干扰。

总结：层让能大幅优化游戏，持有非常精细的世界而不产生任何性能问题。用户实测性能提升超过 200–300%。 由于层流式范围是动态值，玩家甚至可以在设置中调整这个范围。

记住：不要让所有层同时加载。 例如，当用 500×500 网格加载地形时，尝试用 350×350 网格流式加载对象——这样 500 和 350 的层不会同时加载，因为地形会在位置 0、500、1000 加载，而其他对象在 0、350、700、1050 等位置加载（网格边界错开，避免同时刷新）。

9. 局部区域更新器（Local Area Updater）

Local Area Updater 在以下场景中很有用：几位开发者在同一区域工作，但在不同层上；或者他们在同一世界的同一层上工作，但在不同的地方/区域。这里的"层"指——AI、FX、模型、灯光、大模型、小模型、地形。

9.1 局部区域更新器选项

  1. 打开一个空场景并保存。可以把它称为 “Local Area Updater Scene”（局部区域更新器场景）。

  1. 打开 Local Area Updater 窗口：Tools → Nature Manufacture → World Streamer → Local Area Updater。
  • Scene Collections（场景集合）：这里可以添加一个或多个场景集合预制体。系统会从这些 “scene collections” 中为加载切分场景（虚拟网格元素）。如果使用多个层，记住层的正确顺序。 当使用空前缀的层并点击 “Split Scenes” 时，系统可能会把模型放进错误的场景！空前缀的 Scene Collection 应该放在列表最后。
  • Loading distance（加载距离）：已加载世界的范围。它可以按虚拟网格元素（场景）或 Unity 单位计——可以用下面的复选框选择。当勾选 Unity 单位选项时，Unity 单位距离会被重新计算为虚拟网格元素。当要加载的层拥有不同的虚拟网格元素尺寸时，Unity 单位很有用。 例如：想加载属于某地形区域的 Terrain、模型和 FX。Terrain 与模型和 FX 在不同层，且虚拟网格元素尺寸与它们不同。这种情况下应该使用单位尺寸加载距离。
  • Loading center（加载中心）：XYZ 位置，Local Area Updater 会在上面指定的范围内围绕它加载模型/对象。很快还会加入跟随 Unity 编辑器相机的流式加载。
  • Load scenes from collections around Center point（围绕中心点从集合加载场景）：立即从所选场景集合中，围绕选择的点、在设置的范围加载场景。
  • Load all scenes from collections（从集合加载所有场景）：立即加载与所选场景集合关联的所有场景。
  • Unsplit scenes（取消切分场景）按钮：当想从切分场景（虚拟网格元素）创建大场景时很有用。只需从集合中加载所有场景，然后点击 “unsplit”，就又得到了包含所有模型的大场景。通过这个按钮可以合并层，因为只是移除了它们的虚拟网格元素归属。
  • Split scenes（切分场景）按钮：把新添加或移动的模型放入正确的场景、层和虚拟网格元素。
  • Save loaded scenes（保存已加载场景）按钮：立即创建新场景或用在虚拟网格元素中做的修改更新旧场景。它会更新场景，但在点击 “Save loaded scenes” 之前，必须先点击 “Split scenes” 按钮。它会弹出一个 Unity 的 bug 窗口，只需点击确定或回车。这个窗口包含更新的场景列表。如果列表太大，Unity 窗口会出 bug，无法修复它——别管它，点回车就行。
  • Unload loaded scenes（卸载已加载场景）：移除加载的场景，会回到干净的空场景。
  • Remove empty virtual grid elements（移除空虚拟网格元素）：通过这个按钮，可以从场景集合中移除空场景。这会避免游戏过程中加载空场景。
  • Delete empty scenes（删除空场景）：从项目中删除空场景。有时保留它们是有用的——例如，如果打算在这个区域放新模型，系统就不必再创建新场景了。所以可以保留空场景，在工作结束时清理它们。

9.2 工作区设置、虚拟网格加载、世界刷新

  1. 打开空场景并保存为 “Local Area Updater Scene”。
  2. 打开 Local Area Updater 窗口。
  3. 设置要加载的层数。Scene Collections → 点击箭头 → 数字/尺寸类型。
  4. 把场景集合预制体拖入列表。如果使用多个层，记住层/场景集合的正确顺序。 当使用含空前缀层的场景集合并点击 “Split Scenes” 时，系统可能会把模型放进错误的场景！空前缀的场景集合应该放在列表最后。
  5. 以虚拟网格元素（场景）或 Unity 单位设置要加载的区域大小。
  6. 设置要加载区域的起点——“Loading Center”（加载中心）。
  7. 点击 “Load Scenes from Collections around Center Point”，系统会立即在指定范围内从所选场景集合加载虚拟网格元素（场景）。
  8. 做想做的修改，例如：添加对象、移除、用新区域扩展世界、移动对象。
  9. 点击 “Split Scenes” 按钮，它会把新旧内容排序、移动到正确的层和虚拟网格元素。注意：如果使用了空前缀的层并且它在场景集合列表的顶部，那么一切都会被移入这一层，列表其余部分什么都不会留下。
  10. 点击 “Save loaded Scenes”，这会保存修改并刷新/更新场景集合预制体。
  11. “Unload loaded scenes” 会移除所有内容，清理 “Local Area Updater Scene”。
  12. 如果系统必须创建新场景，应该把它们加入 Build Settings。可以通过场景切分器工具来做，或在 “Gameplay” 场景中点击每个 Streamer 对象、点击错误按钮 “Add to build settings”。只有当场景数量有变化时，这个按钮才会出现。

浮点修复与循环（Floating Point Fix and Looping）

处理这个相当简单。这里有一组细节会帮助：

  • AI 生成（AI spawn）：当玩家移动且使用浮点修复系统（无论是否循环）时，玩家位置会时不时被重置。World Mover 脚本保存本地玩家位置（重置后）与真实玩家位置之间的差值。玩家位置 (XYZ) − Current Move (XYZ) = 玩家真实位置（未重置）。 这些值对生成器（spawner）校正生成位置到实际玩家位置很有用。如果是单机游戏，可以通过附加并填写 “Object to Move” 脚本，让生成器跟随玩家移动。查看 “4.5 浮点修复系统"一节。
  • AI 追击（AI pursuit）：当玩家移动且使用浮点修复系统（无论是否循环）时，玩家位置会时不时被重置。为避免丢失 AI 跟随者：
    • 单机：必须把 “Object to Move” 脚本附加到每个 NPC 对象上，并在开始时用场景中实际的 _World_Mover 对象填充它。更多信息见 “4.5 浮点修复系统"一节。
    • 多人：只需用客户端 World Mover 脚本的 “Current Move” 值校正 RPC/消息中的位置。更多信息见 《4.5 浮点修复系统》一节。

12. 提示、附加信息、性能问题与解决方案

  • 如果纹理流式加载很慢/产生尖峰（“GFX wait for present”），请调整 Quality 设置中的 “Async Upload Time Slice” 和 “Async Upload Buffer Size”。也可以在 Player Settings 里尝试纹理流式加载——“Virtual Texturing”（虚拟纹理）。

  • 只能在带自动连接 Profiler 选项的 Development Build 中检查性能。 在 Unity 编辑器中访问内存非常慢，并会产生许多游戏构建中不会出现的 CPU 尖峰。要减少编辑器中的尖峰，可以暂时关闭静态合批。

  • 如果想从游戏内存中移除纹理，使用 Amplify、Granite 等纹理流式系统。查看 “14. 可能有用的第三方资源"一节。这让可以使用无限分辨率的纹理而不增加内存。Streamer 会运行得极快，因为它只加载碰撞体、网格、地形——纹理由其他外部系统从磁盘流式加载。Unity 已将 Granite 系统引入引擎，现在可以在 Player Settings 的 “Virtual Texturing” 中体验纹理流式加载。

  • 记住把静态对象勾选为 Static！ 这会降低场景流式过程中的 CPU 使用（仅构建时）。如果使用浮点修复系统，必须用自定义工具合批/烘焙对象。

  • 记住勾选 Player Settings 中的 “Prebake Collision Meshes”（预烘焙碰撞网格）复选框，碰撞体流式加载会快得多！但这个选项会让游戏构建时间长得多！最好在最终构建时使用。

  • 建议勾选 Player Settings 中的 “Optimize Mesh Data”（优化网格数据） 复选框，这会减小游戏包体和流式时间，但会极大地延长构建时间！所以只在最终构建或时间充裕时勾选。

  • 记住在项目中开启 Incremental GC（增量 GC），它大幅加快 GC。可以在 Player Settings 中找到它。

  • 场景中的每个错误或警告都会拖慢流式系统。记住清理场景中的 bug 和错误。

  • 为对象使用尽可能简单的碰撞体！ 如果碰撞体被烘焙（Player Settings），它们加载起来会快得多。无论如何，简单碰撞体对项目更健康。

  • 如果场景太重，把它切成更小的部分，用更大的范围加载。会加载许多小块，从而保证更好的性能。好办法还有用第二个 World Streamer 预制体单独加载地形。关键就是：不要一次加载所有东西！

  • 避免！ 加载巨大网格——Unity 会卡在加载这种网格上并产生尖峰。网格的合理大小取决于目标设备。即使是引擎导入过程，大网格也很慢。

    • 记住：地形细节分辨率、控制纹理分辨率、基础纹理分辨率和高度图分辨率都会影响流式性能，所以要明智地调整。如果不需要那么多细节，通过设置更低值来削减未使用的数据。
  •  如果垃圾回收器（GC）尖峰过重，可能是场景中的对象太多，或者 Unity 地形的 splatmap 太大（听起来傻但确实如此）。可能会在 **GC.Mark.Dependencies** 函数处出现尖峰，它与场景中的游戏对象数量相关。可以通过**调整层**来减少它——场景中只应保留真正需要的东西。这也可能是/Unity 脚本的内存泄漏 bug。可以在脚本中自行更改 GC 的调用频率，或移除它、由自己的脚本时不时调用。无论如何记住：**如果有 GC 尖峰，说明做了些不对的事。** 也可能是 Unity 的 bug——有时 Unity 函数也会有内存泄漏。

  • 用环形流式，可以在远处把沉重的 Unity Terrain 替换为低模网格。这能节省数百 MB 内存、避免 CPU 尖峰、消除 Unity Terrain 刷新持续产生的静态 CPU 占用……通过把树替换为低模网格，能节省数千个批次。

  • 树、草和大量同类对象尽量使用实例化（instanced）对象。 在引擎中加载巨大的静态合批烘焙网格更慢。实例化对象只加载一次，而且非常快，然后在场景中大量填充。与其加载 MB 级数据，只往内存加载几 KB。（注：此处指 GPU Instancing——用少量网格引用绘制大量同型对象，而非逐个加载完整网格数据。）
