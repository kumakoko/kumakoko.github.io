1 切分.unity场景后共享使用光照贴图的问题

World Streamer 插件文档的Lighting Settings 选项中说：“这个Lighting Settings是为切分生成的场景设置的。可以为它们设置特定的光照选项，这样所有场景都会包含相同的 lightmap、烘焙 ambient 等设置。这可以避免流式加载过程中的警告和错误。它还可用于 切分的 Light Probe（光照探针） 并把它们分发到流式场景中”，这是不是指：所有的切分后的生成的场景，都用的是同一份光照贴图，即是切分前的大场景的那张光照贴图？

用户的理解基本正确，但需要厘清两个层面：

1.1. Lightmap 本身：确实是大场景烘焙的那一套，切分不会重烘

切场景时，每个 Renderer 身上的两个关键数据原样保留：

  • lightmapIndex——用哪张 lightmap 图集
  • lightmapScaleOffset——在该图集上的 UV 区域

所以切分后所有 tile 里的物体，采样的仍是切分前在 Work 大场景里一次性烘焙出来的 lightmap 资产。这样做的好处正是跨 tile 边界光照连续，不会出现每个 tile 各烘各的接缝和漏光。

1.2. 但 “same lightmap” 的重点是"引用和设置统一"，不是每场景复制一份贴图

Unity 每个场景自带一份 LightmapSettings / RenderSettings（ambient、fog、baked ambient 等）。大场景切成几十个 tile 后，如果某个 tile 丢失 lightmap 引用或设置不一致，运行时多场景叠加加载时就会出现 renderer references invalid lightmap 之类的警告，物体发黑。

这个 Lighting Settings 选项做的事，就是把同一份 lightmap 资产引用 + 相同的 ambient/fog 等设置写进每个生成的 tile 场景。磁盘上的 lightmap 纹理（exr / LightingDataAsset）只有一份，是被多个场景共享引用的资产，不是每场景各存一份。手册原文也说，初始设置直接取自当前 Work 场景，Work 场景设置正确的话其余项不用再动。

1.3. 两个容易误解的细节

  • 不一定是"一张"贴图：超大世界烘焙时 Unity 受最大图集尺寸限制会输出多张图集，“same lightmap” 指的是同一套图集。
  • 内存代价：因为每个 tile 都引用整套图集，只要加载任一 tile，整套 lightmap 就进内存（纹理按资产去重复用），lightmap 不会随 tile 卸载而分块卸载。超大世界通常配合：把光照单独切成一个 Lighting 层全局加载一次，或用 Unity 的 lightmap mip streaming / 虚拟纹理方案。

1.4. Light Probe 的机制恰好相反

探针是真的被切开了：源 Light Probe Group 按 tile 尺寸切成多份，分别移入、重命名到各层切分后的场景文件夹，原始 grid 会被禁用以防重复。所以探针是随 tile 真正分块流式加载/卸载的——这与 lightmap 纹理的全局共享正好形成对比。

一句话总结：Lightmap = 大场景一次烘焙、全 tile 共享引用的全局资产；Light Probe = 按格子真切开、随场景流式分发。

2 超大场景烘焙光照图的问题和方案

现在有一个问题就是，如果有个超大场景，10公里乘以10公里，烘焙光照图会很慢吧？有什么提速的方法?

是的，10km×10km 如果当一个整场景、按默认参数烘焙，会非常慢，而且光图集数量会爆炸。但慢的根源不是"场景大"，理解下面这个公式就抓住了关键：

烘焙耗时 ≈ 光贴图纹素总数 × 每纹素的采样成本 纹素总数 = Lightmap Resolution² × 参与烘焙的表面积

10km×10km = 1 亿平方米，即使按 1 texel/米的低分辨率算，光地形就要 1 亿纹素（约 24 张 2048 图集），按默认 2 texel/米就是 4 亿。提速就是围绕"砍纹素数"和"砍单纹素成本"两件事，再配合分批烘焙。

2.1 砍纹素数量（收益最大，通常能快 10 倍以上）

  1. 全局 Lightmap Resolution 降到 0.2~0.5 texel/单位，地形单独控制在 0.1~0.2。
  2. 按重要性分级（这是大场景的标准做法）：
    • 近处建筑/英雄物件：MeshRenderer 的 Scale In Lightmap 设 2~4
    • 普通物件：1
    • 远景/地形：0.1~0.25
    1. 小物件不要烘焙：石头、小道具、栅栏这类关掉 Contribute GI，改用 Light Probe 接收间接光，视觉几乎无差但省掉海量图集。
  3. 只给真正需要的物体勾选 Static / Contribute GI，默认全选 Static 是烘焙灾难。
  4. Lightmap Padding 在可接受范围内调小（如 20→8~16）。

2.2 降低每个纹素的成本（Unity 2022.3 推荐配置）

  • Lightmapper 换成 Progressive GPU（2022.3 已成熟，通常比 CPU 快数倍）。前提是显存够（建议 12GB+），显存不足会自动回退 CPU；烘焙时关掉其他占显存的程序。
  • 开启降噪器（Optix（NVIDIA）/ OpenImageDenoise），这是第二大提速点——有降噪时采样数可以大幅降低：
    • Direct Samples：16~32
    • Indirect Samples：64~128
    • Environment Samples：64
    • Bounces：1~2
  • 关掉 Baked AO（或调很低），AO 靠贴图/材质表现即可。
  • Max Lightmap Size 用 2048 即可，图集过多本身也有开销。
  • 灯光用 Mixed + Shadowmask，而不是全 Baked 多光源；动态光只留必要的。

2.3 分块烘焙——和 WorldStreamer 流水线最契合的方案

这是关键认知：10km 场景不应该烘一张（或一套）全局大图。正确顺序是先切成 tile（比如 500m×500m = 400 块），再逐块烘焙：

  • 每块场景烘自己的小 lightmap，运行时随 tile 流式加载和卸载——这恰好解决了上一轮说的"全局 lightmap 常驻内存"问题。WorldStreamer 的 Lighting Settings 照样把统一的 ambient/fog 设置同步给每块即可。
  • 防接缝做法：烘焙某一块时，把相邻块以 Additive 方式一起加载（隐藏渲染也行），让邻块几何参与间接光反弹和阴影计算，烘完只保存当前块。间接光是低频的，这样基本无缝。
  • 可以脚本化：调用 Lightmapping.BakeMultipleScenes(...) 批量处理，或用命令行 -batchmode 在另一台机器上夜间无人值守逐块烘。
  • 规模感受一下：500m tile、0.3 texel/米 + 建筑加密，一块约 7.5 万~20 万纹素，一张 1024 图集都装不满，单块通常几分钟内完成。

2.4 第三方/替代方案

  • Bakery：Unity 大场景开发里最常用的第三方 GPU 光照贴图器，同质量下通常比 Progressive 快很多，原生支持 URP 和分块工作流，预算允许值得考虑。
  • 远景干脆不烘焙：远景环带用简单 Shader + 顶点色 AO + Light Probe，只对玩家活动近区做全质量烘焙。
  • 动态物体和植被全部走 Light Probe（探针烘焙极快，几乎零成本）。

2.5 推荐起步配置（2022.3 + URP）

项建议值
LightmapperProgressive GPU
全局 Resolution0.2~0.3（地形 0.1）
近景物件 Scale In Lightmap2~4
Direct / Indirect / Env Samples16 / 64~128 / 64
Denoising开启（Optix/OIDF）
Bounces2
Padding / Max Size8~16 / 2048
小物件不烘焙，走 Light Probe

一句话总结：先切 tile 再分块烘焙、分辨率按距离分级、GPU Lightmapper + 降噪、小物件走探针——这套组合下来，10km 场景的总烘焙时间通常能从"按天算"降到"按小时算"，而且还顺带解决了 lightmap 内存常驻的问题。

3 整块大场景烘焙还是切开若干小场景分开烘焙？

上面第三个方案“分块烘焙——和 WorldStreamer 流水线最契合的方案”。不正是和前面分析的“要整个场景烘焙，切分小场景后再烘焙会有光照效果不对”的相矛盾了吗

不矛盾——它们其实是两种不同的工作流，而上一轮在说"分块烘焙"时省略了一个关键前提，导致看起来像冲突。现在进一步说明这个问题。

3.1 区分两种模式

模式 A：先烘后切（WS Lighting Settings 描述的）模式 B：先切后分块烘（我上轮的第三方案）
流程大场景整体烘焙 → SceneSplitter 切分 → 切分器原样保留每个 renderer 的 lightmap 引用先切成 tile → 逐块加载、逐块烘焙
Lightmap 归属全 tile 共享同一套图集每个 tile 有自己的图集
边界光照天然无缝（本来就是一起算出来的）需要措施才能无缝（见下）
烘焙速度慢，只能整体一次算完快，可分批、可重烘单块
Lightmap 内存加载任一块 → 整套图集常驻，无法按 tile 卸载随 tile 加载/卸载

3.2 关键：之前说的"分块烘焙会不对"是有前提的

“各烘各的会有接缝漏光"这句话，成立的条件是——孤立地烘每一块：场景里只加载这一个 tile，Lightmapper 看不到隔壁的地形和建筑，边缘纹素的间接光反弹算少了，隔壁楼投过来的阴影也丢了，于是边界发亮/发黑。

而模式 B 的正确做法是重叠烘焙（bake with neighbors loaded）：

  1. 烘 tile B 时，把相邻的一圈 tile（或至少边缘外几十~上百米内的物体）一起 Additive 加载进来；
  2. Lightmapper 计算间接光反弹和阴影时能看到邻块几何，B 边缘纹素得到的光照贡献和整体烘焙时几乎一致；
  3. 烘完只保留 B 的光照数据，邻块恢复原状。

间接光是低频信号，邻块只要"在场参与计算"即可，不需要它们的光图结果。工程上更简单的实操是：按 3×3 加载、整组烘焙、只保存中心 tile 的场景和光图、丢弃其余产物，脚本循环平移即可。

所以准确的表述是：

“孤立分块烘” → 必然接缝；“带邻块参与的分块烘” → 基本无缝。

3.3 模式B确有三个真实的残余成本

  1. 跨边界阴影：烘焙时邻块在场，建筑投到隔壁地面的阴影能正确进入那块的 shadowmask；静态阴影画在地面光图上，运行时不需要投射建筑还在场。但改动一栋边界建筑后，必须连带重烘相邻块，否则阴影是旧的。
  2. Light Probe 边界插值：探针按 tile 切开后，单块加载时边界附近缺邻块探针配合，动态物体在格子边缘可能采到偏差探针。对策是探针布置时在边界外冗余一圈，或让流式加载范围天然重叠（玩家还没走到边界，邻块已加载，2022.3 多场景探针会合并四面体剖分）。
  3. ambient/fog 等设置仍需统一：WS 的 Lighting Settings 那部分功能在模式 B 下照用——只是不用它"共享同一套 lightmap 引用"的部分，只用它同步 RenderSettings。

3.4 实际项目怎么选

  • 10km 但 tile 数量不极端、光图总量在显存/内存预算内 → 模式 A 最省心，光照质量零风险，这也是 WS 设计上的默认路径；
  • 世界超大（几十 km、上千 tile）或需要频繁局部修改、需要 lightmap 随 tile 卸载 → 模式 B，接受脚本化重叠烘焙和连带重烘的纪律；
  • 常见的混合做法：玩家主城/出生点等高频区域用模式 A 全局精烘，广袤外围用模式 B 分块烘，两套层各自流式加载。

一句话：矛盾是表面的——“先烘后切"和"带邻块的分块烘"都对，错的只有"不带邻块、孤立地分块烘”。

4 不用Mesh用Terrain能烘焙吗？

在Unity3D引擎中，如果场景中使用的是Terrain，而不是Mesh的话，能烘焙吗？有什么要注意的事项？

这是个好问题，Terrain 的烘焙机制和普通 Mesh 有不少差异。我先快速核实一下 Unity 2022.3 下地形分块与光图集的具体规则，避免凭印象讲错。

能烘焙，而且 Progressive Lightmapper 对 Terrain 是完整支持的——Terrain 本质上就是引擎动态生成的网格，只是它的光图 UV、分块规则和普通 Mesh 不一样。下面这些差异点是用 Terrain 时真正需要注意的。

4.1 怎么开启

  • 在 Terrain 设置（齿轮图标）里勾选 Lightmap Static（等同于把地形 GameObject 标 Static 中的 Lightmap Static），不勾则完全不参与烘焙。
  • 不需要也不能手动生成 Lightmap UV（UV2）：Terrain 的光图 UV 由引擎内部按世界坐标生成，你导入模型时那套 “Generate Lightmap UVs” 对它不适用。

4.2 最大的坑：纹素密度按 XZ 平面投影，陡坡会"偷分辨率”

Terrain 的光图 UV 是按地形在 XZ 平面上的位置摊开的，与实际起伏后的表面积无关。后果是：

  • 平坦地面纹素分布均匀；
  • 陡峭的山崖、垂直坡面，几何被拉长了但光图纹素没增加，陡坡上的光图会糊、阴影发虚。

这是机制限制，没法像 Mesh 那样靠展 UV 解决。陡坡处的明暗建议更多依赖贴图 AO、法线和实时/混合光，而不要指望光图细节。

4.3 Terrain 没有 Scale In Lightmap——分级靠"分层 + 不同 LightingSettings"

普通 MeshRenderer 可以单独设 Scale In Lightmap，Terrain 没有这个参数，它直接吃场景的全局 Lightmap Resolution。想让地形用低分辨率、建筑用高分辨率，标准做法是：

  • 把 Terrain 单独放一个层（WS layer）/ 单独的 additive 场景，用一份低分辨率的 LightingSettings（如 0.1~0.2 texel/米）烘焙；
  • 建筑、道具在另一个层，用高分辨率 LightingSettings（如 1~2）烘焙；
  • 运行时两类场景叠加加载，各自光图独立。

这恰好和 WorldStreamer 的分层流式体系天然匹配，也是大世界项目处理地形光图的通用模式。

4.4 树和草默认都不进光图

这是 Terrain 烘焙最容易被误解的地方：

  • 草（Detail）完全不参与烘焙，只能用简单着色 + Light Probe；
  • Terrain 上刷的树也不是 Static Renderer，不会被单独打进光图集。树的光照有两条路：
    • Terrain 设置里勾选 Bake Light Probes For Trees——引擎在每棵树位置生成内部探针，树按探针受光（这些内部探针不影响其他物体）；
    • 或让树受场景中的 Light Probe Group 影响。
  • 如果需要树在地面投下清晰的烘焙静态阴影，默认流程做不到；常见办法是关键区域用真正的静态树 Mesh 替代刷树，或用 Bakery 这类工具的 “export terrain trees” 功能把树转成可烘焙对象。

4.5 内部按 Patch 切块，图集利用方式与 Mesh 不同

引擎把 Terrain 按内部 patch（小块）划分，每个 patch 是光图集里一张独立 chart，chart 之间同样吃 padding。所以：

  • Heightmap Resolution 越高，patch 越多，光图集里的 chart 和 padding 浪费也越多——不要为了光图去堆 heightmap 分辨率，heightmap 只按几何精度需求设；
  • 真正决定光图总量的还是 地形世界尺寸 × 光图分辨率。10km 整块地形按高分辨率烘，一样是图集灾难。

4.6 和 WorldStreamer 流水线配合时的注意点

  1. 先用 Terrain Manager 把地形切成 tile（如 500m×500），每块生成独立的 TerrainData，再逐块烘焙——顺序与上一轮讨论的模式 B 一致。

  1. 分块烘焙时同样要带相邻 tile 一起加载参与计算，否则边界间接光和接缝不对；地形边界处 splat 高度本来就对齐，接缝比 Mesh 场景更容易处理。

  1. 改了地形（高度、splat、挖孔）必须重烘对应块；改边界附近地形要连带重烘邻块。地形挖孔（Paint Holes）现代 Lightmapper 是支持的。

  1. WS 手册特别提醒：如果一个层里同时含 Light Probe 和 Terrain，切分探针后该层必须重新生成。

  1. Cast Shadows 用 Two Sided 时注意：Progressive 支持双面阴影烘焙，旧 Enlighten 不支持。

4.7 材质/Shader 相关

  • URP 下用 Terrain Lit shader，烘焙反照率和反弹一切正常；
  • 如果用自定义地形材质，shader 必须包含 Meta Pass，否则烘焙时取不到地表反照率，地形反弹光会发暗甚至按黑面算；
  • Lightmapper 会通过 splatmap + 各 Terrain Layer 的 albedo 计算地表反照率，Terrain Layer 的 albedo 贴图本身要正确（别把美术工作流里的增强对比度版本误当成 albedo）。

一句话总结：Terrain 能烘，但要记住四条——光图 UV 是 XZ 投影（陡坡吃亏）、没有 Scale In Lightmap（靠分层用不同烘焙分辨率）、树草不进光图（走探针）、先切 tile 带邻块再烘。

4.8 补充说明

2022.3.62f3c1版本的Unity，Terrain里有确有Scale In Lightmap选项

  1. 核实结果：Terrain 确实有 Scale In Lightmap——序列化字段名就叫 m_ScaleInLightmap，语义和 MeshRenderer 的同名参数完全一致：该地形实际烘焙分辨率 = 全局 Lightmap Resolution × 这个 scale。设为 0 则地形本身不烘焙，但仍参与其他物体的光照计算。当前打开的测试场景里有 17 块地形（BasicTerrain 0_0 ~ 3_3 等），它们的值全部是 0.8，和看到的一致。

  1. 没有公共运行时 API：MeshRenderer 有 scaleInLightmap 属性可在代码里改，而 Terrain 类型没有暴露这个属性（Terrain 公共接口只有 lightmapIndex / lightmapScaleOffset 等）。想批量调整只能在编辑器下通过 Inspector，或用 SerializedObject 写 Editor 脚本改 m_ScaleInLightmap。

  1. 它是 Terrain 组件自身的字段，所以存在 Terrain 被切分后的每个 tile 上——WorldStreamer 切完后，每块 tile 地形可以分别设不同的 scale（比如外围 tile 设 0.2、主城 tile 设 1）。

  1. 对上面第三点“Terrain 没有 Scale In Lightmap”的修正：之前说"Terrain 想降低光图分辨率只能靠分层 + 不同 LightingSettings"——这是错误的。直接把 Scale In Lightmap 调低就行，同一场景里地形 0.2、建筑保持 1，一次烘焙即出效果，不必为此分层。分层烘焙仍然有价值（分块并行、光图随 tile 卸载），但那是流式组织的需要，不是"分辨率分级"的前提。
