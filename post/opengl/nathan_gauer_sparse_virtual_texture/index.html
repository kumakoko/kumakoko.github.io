稀疏虚拟纹理

稀疏虚拟纹理(sparse virtual texture)。简单地说，就是在着色器中重新实现分页（pagination），可以拥有无限的纹理，同时保持 GPU 内存使用量恒定。

步骤 1 - 手工制作分页


分页概述


要理解 SVT 如何工作，首先要了解什么是分页：

在大多数计算机上，数据存储在 RAM 中。RAM 是一个线性缓冲区，其第一个字节位于地址 0，最后一个字节位于地址N。因为某些原因，使用真实地址并不方便。因此有人发明了分段（segmentation），后来演变为分页。这个想法很简单：使用虚拟地址（virtual address），由 CPU 将其转换为实际 RAM 地址。

在上图中：左侧是虚拟内存，可以看见虚拟内存的地址是线性连续的。共分为4个page。虚拟内存中每个page，都线性映射到page table中的一个entry。

下面举例说明，利用page和page table，如何将一个virtual RAM address（VRA）映射到physical RAM address（PRA）。例子中的page的大小是4KB，即4096个字节。每个虚拟地址VRA，可以用公式表示为：

VRA = PageIndex * 4096 + Offset

其中PageIndex表示该page对应于page table中的第几个entry，从0开始算起。4096就是page的大小4KB，Offset则是该VRA在page中，相对于page起始地址的偏移值。

  1. 假如有VRA为9416，将其除以4096，得到商为2，余为1224。
  2. 上一步得到的商就是PageIndex值，余数就是Offset，这表示，VRA=9416的地址，对应的page table的第2个entry。
  3. 假定第2个entry记录的实际物理页空间的首地址为20480，则PRA = 20480 + Offset = 21704

获取你的记忆地址。 地址 = 9416 将其拆分为页面对齐的值和其余部分。 9416 => 8192 + 1224。 对齐地址 = 8192 休息 = 1224 取对齐值，然后除以页面大小。 8192/4096 = 2 索引 = 2 这个结果就是页表中的索引。 读取此索引处的页表条目，这是您的新对齐地址： 页表[2] = 20480 将其余内容添加回此地址： 物理地址 = 20480 + 1224 您有您的实际地址。 将页面概念添加到着色器 为了实现这种技术，我需要：

查找要加载的页面 将它们加载到“主内存”中 添加此分页表/翻译技术。 这可以使用计算着色器和线性缓冲区来实现，但为什么不直接使用纹理呢？这样，我只需添加一个特殊的渲染过程来计算可见性，并修改我预先存在的前向渲染过程以支持分页表。

第一步是构建页表查找系统。这是在 GLSL 中完成的：

取 UV 坐标 将它们拆分为页面对齐的地址，其余的 计算 X 和 Y 维度的页面索引 在计算索引处查找纹理（我们的页表） 增加其余的价值 uv 坐标 显示 UV 坐标 页面对齐 UV 显示页面对齐的 UV 坐标 计算可见性 分页的另一个优点是能够在运行时加载/卸载部分内存。内核不会加载整个文件，而是只加载所需的位（页面），并且只在需要时获取新页面。

这是使用页面错误完成的：

用户尝试访问尚未加载的地址。 CPU 故障，并向内核发送信号（页面错误）。 内核确定是否允许此访问，并加载页面。 一旦加载，内核就可以恢复用户程序。 这种机制需要硬件支持：CPU 知道什么是页表，并且有这个中断系统。在 GLSL/OpenGL 中，我们没有这样的东西。那么当中断不存在时我们该怎么办？我们轮询！

对于我们来说，这意味着运行初始渲染过程，但我们不是使用灯光和材质渲染最终输出，而是输出页面地址。（类似于上面看到的插图）。

这是通过绑定一个特殊的帧缓冲区并进行渲染到纹理来实现的。一旦完成该过程，就可以读取输出纹理，然后我们就可以发现哪些页面是可见的。

对于此渲染过程，所有材质都被一个简单的着色器替换：

#version 420 core

/* material definition / uniform float textureid; / Size of a page in pixels. / uniform float page_size; / Size of the pagetable, in pixels (aka how many entries do we have). / uniform float pagetable_size; / Size in pixels of the final texture to load. / uniform float texture_size; / Aspect ratio difference between this pass, and the final pass. */ uniform float svt_to_final_ratio_w; // svt_size / final_size uniform float svt_to_final_ratio_h; // svt_size / final_size

in vertex_data { vec2 uv; } fs_in;

out vec4 result;

/* Determines which mipmap level the texture should be visible at.

  • uv: uv coordinates to query.

  • texture_size: size in pixels of the texture to display. */ float mipmap_level(vec2 uv, float texture_size) { vec2 dx = dFdx(uv * texture_size) * svt_to_final_ratio_w; vec2 dy = dFdy(uv * texture_size) * svt_to_final_ratio_h;

    float d = max(dot(dx, dx), dot(dy, dy)); return 0.5f * log2(d); }

void main() { /* how many mipmap level we have for the page-table */ float max_miplevel = log2(texture_size / page_size);

/* what mipmap level do we need */
float mip = floor(mipmap_level(fs_in.uv, texture_size));

/* clamp on the max we can store using the page-table */
mip = clamp(mip, 0.f, max_miplevel);

vec2 requested_pixel = floor(fs_in.uv * texture_size) / exp2(mip);
vec2 requested_page = floor(requested_pixel / page_size);

/* Move values back into a range supported by our framebuffer. */
result.rg = requested_page / 255.f;
result.b = mip / 255.f;

/* I use the alpha channel to mark "dirty" pixels.
 * On the CPU side, I first check the alpha value for > 0.5,
 * and if yes, consider this a valid page request.
 * I could also use it to store a "material" ID and support
 * multi-material single-pass SVT. */
result.a = 1.f;

} 一旦检索到页面请求列表，我就可以加载“主内存”中的纹理。

主存储器是一个简单的二维纹理，页面分配现在很简单：第一个请求的页面获得第一个插槽，依此类推，直到内存满。

主内存纹理 “主记忆”纹理 一旦分配了页面，我需要更新相应的页表条目以指向正确的物理地址。这是通过更新页表中的正确像素来完成的：

R＆G通道存储物理地址。 B 未使用。 A 标记该条目为有效（已加载）或无效。 分页表 分页表纹理 渲染过程 最后一遍和经典一遍非常相似，只是我不是绑定一个漫反射纹理，而是绑定了两个纹理：分页表和内存。

绑定 3D 模型 绑定 GLSL 程序 绑定页表和主内存纹理。 在这个阶段，我可以显示一个太大而无法在 RAM 和 VRAM 中容纳的纹理。

步骤 2：MipMapping 如果你看一下前面的视频，你会注意到两个问题：

屏幕边缘附近出现红线。 缩小时页面加载增加。 第一个问题是纹理加载不会阻止当前通道。这意味着我可能会请求一个页面，但在运行最后一个通道时它还没有准备好。我可以将其渲染为黑色，但想让它可见。

第二个问题是因为我的虚拟页面大小和纹理页面大小之间有 1:1 的映射。缩小以显示整个平面需要加载整个纹理。纹理不适合我的 RAM。

这两个问题的解决方案都是 mipmaps。

mipmap 级别 0 的页面覆盖page_size像素。 mipmap 级别 1 的页面覆盖page_size * 2像素 … mipmap 级别 N 的页面覆盖整个纹理。 现在，我可以默认加载 mipmap 级别 N，如果请求的页面不可用，我只需在 mip 级别中向上移动，直到找到有效的页面。

添加 mipmap 还允许我实现更好的内存回收机制： 我现在可以用上一级的一个页面替换 4 个页面。 因此，如果我的内存不足，我可以降级某些区域，这样可以节省 75% 的内存。

最后，MipMapping 降低了带宽要求：如果物体很远，为什么要以高分辨率加载纹理？低分辨率页面就足够了：

更少的磁盘负载。 更少的内存使用。 更少的延迟（因为需要加载的页面更少）。 具有 MipMapping 的物理地址 使用 MipMapping 显示物理地址 步骤 3：复合材料 初始渲染具有 PBR 材质。此类材质不仅具有反照率贴图，还具有法线和粗糙度+金属贴图。要添加新纹理，有几种选择：

新的内存纹理、新的页表纹理、新的通道。 简单的 需要额外通行证。这不行。

相同的内存纹理，相同的页表纹理。 每个页面实际上按顺序包含 N 个纹理。因此，当加载一个页面时，会查询并加载 N 个纹理。 易于实现，但我必须加载 N 个纹理。

相同的内存纹理，多个页表纹理。 页表很小，16x16 或 32x32。开销不是很大。 我可以卸载一些远处物体的通道（例如法线贴图）。 缺点是我现在在着色器中有 N*2 个纹理采样：每个纹理一个，以及与其相关的页表一个。 因为我喜欢最后一个选项的灵活性，所以我选择实现它。在最终版本中，每个对象都有 4 个纹理：

内存（1 mip 级别） 反照率分页表（N mip 级别） 粗糙度/金属分页表（N mip 级别） 正常分页表（N mip 级别） 在下面的演示中，页面加载在主线程中完成，但每帧限制为 1 个页面，使加载过程非常直观。

左下图显示的是主内存。 其他图表显示了页表及其对应的 mip 级别。

页面请求：子采样、随机和帧预算。 对于每一帧，我都需要进行初始检查以检查纹理可见性。在每一帧之间在 CPU 上读取此帧缓冲区非常慢，对于 4K 输出来说，这非常昂贵。

好消息是：在这种情况下，我不需要 4K 帧缓冲区！页面覆盖 N 个像素，因此我们只需减小帧缓冲区大小，并希望我们的页面仍会被请求！

上面的演示使用的是 32x32 帧缓冲区。这非常小。如果操作不当，这将无法正常工作：某些页面会卡在 2 个渲染像素之间，并且永远不会加载。

缺页 8x8 帧缓冲区，无抖动。

解决这个问题的方法是给初始传递添加一些抖动。页面请求视点不完全是相机的位置，而是相机的位置 + 一些随机噪声。

这样，我们可以在不增加帧缓冲区大小的情况下增加覆盖范围。
